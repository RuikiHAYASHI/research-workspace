### 7.18 記録づくりの窓の中身の形と時刻（2026-11-05）

**林の問い**（図には載せない）: 窓の中は「記録の積み重ね + 画像列」なのか。時刻はどう付くのか（3 秒で Silence なら「3s: </Silence>」のようになるのか）。画像列にも時刻は付くのか。

- 窓の中は、**1 秒ごとに「ユーザー = 映像」「アシスタント = 返事」が交互に並ぶ会話**。記録の一覧と画像列を分けて置く形ではない。直近 32 組を残し、残った先頭のユーザー発話に指示文を付け直す

  ```text
  [user]      <3.1 seconds>[映像 2 枚]<3.6 seconds>[映像 2 枚]<3.0-4.0 seconds>
  [assistant] </Silence>
  [user]      <4.1 seconds>[映像 2 枚]<4.6 seconds>[映像 2 枚]<4.0-5.0 seconds>
  [assistant] </Observe> [4.0 seconds] （細部の文）
  ```
- **回答に使う記録は、会話とは別の一覧**。Observe・Summary の返事だけを（種類, 始まり, 終わり, 文）で保存する。Silence は入らない。時刻はその返事を出した 1 秒の区間（Summary の始まりは前の Summary の後の最初の Observe）。回答のときは `[4s-5s] （文）` の行にして、Summary の一覧 → Observe の一覧の順に並べる

### 7.24 PSTL の説明（2026-11-05）

**林の今の理解**: Silence が大量に出るので、制御トークンが切り替わったタイミングで loss を計算する、くらい。

### 7.25 学習について原文に書いてあることの詳しい解説（2026-11-05、AI の説明）

**林の依頼**: 学習については、書いてあることを詳しく解説してほしい（質問した範囲だけでなく）。

#### 0. 全体
- [著者] Qwen3-VL-4B-Instruct から始め、教師ありの追加学習（SFT）を **1 段だけ**行う（§5 Implementation Details、付録 C.1）。強化学習や、段を分けた学習はない
- 学ぶのは「いつ・何を出すか」の両方。制御トークン（いつ）と、その後の文（何を）を、1 本の因果的な映像と言葉の系列の中で次トークン予測として学ぶ（§1 第3段落、§3）
- 学習コードは公開されていない（再現ログ）

#### 1. 学習の系列の形（§3.1・§3.2・§4.1、付録 B.2）
- 映像の clip と、そのときの正解の出力（制御トークン + 必要なら文）が、時間順に交互に並ぶ。推論のときの会話と同じ形
- [著者] 「見終わる前のことは書かせない（causal）」が原則。記録は、その根拠の区間が終わった時刻に置く。置かれた記録は、それより後の予測からだけ見える（付録 B.2「become available only to subsequent predictions」）
- 動画全体の説明は、動画の最後に「全体を要約して」という指示を足して `</Response>` の正解にする。記録には入れない（付録 B.2）
- 系列の長さは最大 131,072 トークン（映像と文の合計）。複数の例を 1 本に詰めて（packing、soft）学習する（表7）

#### 2. 損失（§3.3、付録 A.1、式1〜3、表5）
- 文の損失: Observe・Summary の後の記録、Response の後の答え・出力は、全トークンを普通の次トークン予測で教える（付録 A.1「retains full next-token supervision」）
- 状態（制御トークン）の損失 = PSTL
  - 出力アンカー A_τ: 文を書き始める制御トークン。PHCM は Observe・Summary、Proactive QA と Proactive Interaction は Response（表5）
  - タスクごとの制御トークン: PHCM は Silence・Observe・Summary、Proactive QA は Silence・Standby・Response、Proactive Interaction は Silence・Response（表5）
  - 1 本の学習の系列の中で、連続する正解の制御トークンの組「X→Y」ごとに数 n_{X→Y} を数える
  - 式1: q = max_X max_{a∈A_τ} n_{X→a}。アンカーへ入る組の中で一番多い数を、その系列のすべての組で共通の上限にする
  - 式2: 各組から min(n_{X→Y}, q) 個を、重複なしで一様にランダムに選ぶ。q 以下の組は全部残る。アンカーへ入る組は定義から全部残る
  - 式3: L_state = −(1/|I|) Σ_{i∈I} log p_θ(z_i | c_i)。選ばれた位置 I だけを平均。c_i はその位置より前の映像と言葉の文脈
  - 選ばれなかった制御トークンも系列には残る（teacher forcing のまま）。後ろの予測からは見え、注意（attention）も遮らない。自分の位置の損失に入らないだけ（付録 A.1）
  - 付録 A.1 の補足: 状態の「持続」は無駄な待ちとは限らない（Observe が続けば、それぞれ別の記録を書き始める）。q は系列ごとに 1 回、全部の「→アンカー」の組から計算して全組で共有するので、アンカーへ直接つながらない組（例 Silence→Silence）も上限で抑えられる
  - 推論のときは PSTL を使わない。外からの切り替えの規則も使わず、学習した分布からそのまま制御トークンと文を出す（§3.3 末尾、付録 A.1）
  - [著者] 結果として、注釈された制御トークンの 27.5% だけを教える（Abstract、表3）
- [AI] 文の損失と状態の損失をどう足し合わせるか（重み）は書かれていない。系列の最初の制御トークン（前がない）の扱い、アンカーへの切り替わりが 1 つもない系列（q = 0）の扱いも書かれていない

### 7.33 「生成」と「予測」の違い、PSTL はいつ計算できるのか（2026-11-05）

**林の問い**: 生成と予測の違いは何か。学習は「質問 → clip1 で予測 → clip2 と clip1 の正解と clip1 で予測 → clip3 と clip2 までの予測で予測…」の繰り返しか。PSTL で損失を計算するには Response まで行ってからでないと話が合わないのでは。

**AI の答え**
- 記録づくりの系列には質問は入らない（§7.28・§7.29）。前回の例（質問 → clip1 …）は Proactive QA の系列
- **予測** = その位置で、次に来るトークンの確率（どれがどれくらい来そうか）を出すこと。**生成** = 予測した確率から 1 つ選んで実際に出し、それを次の入力に足すこと
  - 推論: 予測 → 1 つ選ぶ（生成）→ 自分の出力を次の入力にする、を繰り返す。正解はないので損失もない
  - 学習（teacher forcing）: 予測はするが選ばない。次の入力には**正解**を入れる。予測した確率のうち正解のトークンの確率が低いほど損失が大きい
- 林のまとめの直すところ: clip3 のときに入るのは「clip2 までの**予測**」ではなく「clip2 までの**正解**」。モデルが clip1 で Standby を出しそうでも、clip2 の入力には正解の Silence が入る
- 実際には、正解の系列を前もって全部持っているので、この繰り返しを順番に回すのではなく、系列全体を 1 回で読み、後ろを見ない仕組み（因果的なマスク）で全位置の予測を同時に出す。結果は順番に回すのと同じ
- PSTL: どの位置を損失に入れるかは、**正解の系列だけ**から決まる（正解の制御トークンの組を数えて q を決め、選ぶ。式1・2）。モデルの出力を待つ必要はない。系列の最後（Response と答えの文を含む）まで正解が最初からあるので、話は合う。損失は、系列全体を読んで全位置の予測が出た後に、選んだ位置と文の位置で計算する
- 架空の例（確率は説明用の作り物）: Proactive QA の正解が「Silence, Silence, Standby, Response + 答え」のとき、1 つ目の位置で予測が Silence 0.7・Standby 0.2・Response 0.1 なら、そこの損失は −log 0.7。2 つ目の位置の入力には、モデルの予測に関係なく正解の Silence が入る

### 7.36 林の現時点の理解の確認（2026-11-06）

林のまとめ: 「PHCM は /Observe と /Summary の二段階の組み合わせの仕組み。それを実現するために学習が要る。Proactive QA のようなケースでも、学習で制御トークンの出し方を調整している。学習では PSTL で、データに多い /Silence を学習しすぎないようにする。データは OneStreamer-1M で、PHCM 用・Proactive QA 用・Interaction 用・シンプルな QA 用がある。詳しくはデータを見ないと分からない」

| 林の理解 | 判定 | 補足（根拠） |
|---|---|---|
| PHCM = Observe と Summary の 2 つの組み合わせ | 半分正しい | [著者] PHCM の主眼は「過去のフレームの代わりに、自分で書いた時刻付きの文を残す」こと（§3.2 冒頭）。Observe（細部）と Summary（まとまりの要約）の 2 つの粒度は、その記録の中の構造。「二段階」だと順番に処理する印象になるので「2 種類の記録」の方が近い。記録を書かないときの Silence も PHCM の動きに含まれる（§3.2「Silence は記録を書かずに観測を続ける」） |
| PHCM のメリット | 林は忘れた | [著者] 過去のフレームを持ち続けると今の映像の細部と文脈を取り合い、直近の窓だけだと遠い過去が消える。文の記録なら、窓を広げずに短い文で過去に届く（§3.2、§2）。[実験] 表2: 同じ Recent-16 の窓で、記録ありは ASI 63.5→71.6、リアルタイムの知覚も落ちない（OVO Real-Time 80.9→81.4）。表4: 全部のフレームを持つより TTFT 4.560→0.124 秒。2 種類に分けること自体の効果は付録 E.2・表18（Observe が大部分、Summary は補う） |
| 実現のために学習が要る | 正しい | Proactive Caption Memory の族で教える（付録 B.1） |
| Proactive QA でも学習で制御トークンの出し方を調整 | 正しい | 加えて、答えの文も同じ学習で教えている（損失は文のトークンにもかかる、§3.3「キャプションとタスクの出力は教師をすべて保つ」） |
| PSTL = 多い Silence を学習しすぎない | ほぼ正しい | 対象は Silence だけでなく状態トークン全般（続く Standby なども）。答え始めのトークン（出力アンカー）は全部残し、同じ遷移が続く部分を上限まで間引く。間引いたトークンも入力の並びには残り、状態の損失から外すだけ。文の損失には影響しない。使うのは状態トークンの 27.5%（§3.3、式1–3、表3）。「Silence を減らす」だけなら Random Sparse と同じだが、それは大幅に悪い（表3）ので、「変化と持続の代表を選ぶ」ことが効いている |
| 1M の中身: PHCM 用・Proactive QA 用・Interaction 用・シンプルな QA 用 | ほぼ正しい | 4 つの族と対応（表6）。ただし 4 つ目の Perception & Memory QA の形（その場で答える普通の QA なのか、Silence → Standby → Response の形なのか）は書かれていない（§7.32）。ほかに LLaVA-Video のオフラインデータも混ぜている（§5） |
| 詳しくはデータを見ないと分からない | 正しい | ただし OneStreamer-1M が公開されているかは未確認（§7.25 付近）。学習コードは公開されていない |
