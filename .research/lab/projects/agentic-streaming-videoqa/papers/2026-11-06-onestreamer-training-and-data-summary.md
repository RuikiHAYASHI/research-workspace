## 1. 何を学習するか

- [著者] Qwen3-VL-4B-Instruct（制御トークンを登録済み）から始めて、教師ありの追加学習（SFT）を**1段だけ・1回だけ**行う（§5、付録C.1・表7）。強化学習も、段を分けた学習もない
- 動かすのは projector と LLM。映像のエンコーダ（ViT）は固定（表7）
- 学ぶのは「**いつ**出すか」（制御トークン）と「**何を**出すか」（その後の文）の両方（§1、§3）
  - 記録づくり（PHCM）：いつ `</Observe>`・`</Summary>` を書き、何を書くか
  - Proactive QA・Interaction：いつ `</Response>` で答え、何と答えるか
- PHCM を学習で教える理由：[著者] 過去のフレームを持ち続けると今の映像と入力を取り合い、直近の窓だけだと遠い過去が消える。自分で書いた短い文で過去を残せば、窓を広げずに過去に届く（§3.2）
- 全データを混ぜて学習する。族ごと・状況ごとに別のモデルや別の段で学習してはいない（§5）
- 設定（表7）：最大 131,072 トークン（映像と文の合計）、複数の例を 1 本に詰める（packing）、映像は 1〜4fps・最大 2,048 枚、AdamW、学習率 1e-5→1e-6（cosine）、詰めた系列 128 本で 1 回の更新、1 epoch・1,174 step、H200 32 枚
- 学習コードは公開されていない

## 2. 学習の 1 例は「正解の系列」

- 1 例は、データづくりで**前もって全部作った**正解の並び：映像の clip と、各時刻の正解の出力（制御トークン + 必要なら文）が時間順に交互に並ぶ。Proactive QA などでは最初に質問・指示が入る
- teacher forcing（付録A.1）：モデルは何も生成しない。系列全体を 1 回で読み、後ろを見ない仕組み（因果的なマスク）で、各位置で「それより前だけを見て次を当てる」予測を同時に出す
  - **予測** = 次のトークンの確率を出すこと。**生成** = その確率から 1 つ選んで出し、次の入力にすること
  - 学習は予測だけ。次の入力には常に**正解**が入る（モデルが Standby を出しそうでも、次の入力は正解の Silence）
  - 推論は生成を繰り返すだけで、損失は計算しない。「答えた所で結果から学ぶ」のは強化学習の考え方で、OneStreamer はやっていない
- [著者] 記録は、根拠の区間が**終わった時刻**に置く。置いた記録は、それより後の予測からだけ見える（付録B.2）

## 3. 損失

モデルが出す側の位置すべてで損失を取る。損失は 2 種類ある。

| 損失 | どこに付くか | 間引くか |
|---|---|---|
| 文の損失 | `</Observe>`・`</Summary>` の後の記録の文、`</Response>` の後の答えの文の全トークン | 間引かない（付録A.1「full supervision」） |
| 状態の損失 | 制御トークン（Silence・Standby・Observe・Summary・Response）の位置 | **PSTL で選んだ位置だけ** |

- 入力側（映像のトークン、質問の文）に損失を付けるかは書かれていない（普通は付けない）
- 2 つの損失の足し合わせ方（重み）は書かれていない

### PSTL（§3.3、図4、式1〜3、付録A.1、表5）

- 目的：[著者] Silence が圧倒的に多いので、全部の位置を教えると「待つ」ばかりを覚える。それを抑える
- 対象は Silence だけではなく、状態トークン全般（続く Standby なども）
- 出力アンカー：文を書き始める制御トークン。タスクごとに決まる（表5）

  | タスク | 使う制御トークン | アンカー |
  |---|---|---|
  | PHCM（記録づくり） | Silence・Observe・Summary | Observe・Summary |
  | Proactive QA | Silence・Standby・Response | Response |
  | Proactive Interaction | Silence・Response | Response |

- 手順（**正解の系列だけ**から決まるので、モデルの出力を待たずに計算できる）
  1. 隣り合う正解の制御トークンの組「前→今」ごとに数を数える
  2. 式1：アンカーへ入る組の中で一番多い数を q とする（系列ごとに 1 つ）
  3. 式2：各組から min(数, q) 個を重複なしでランダムに選ぶ。アンカーへ入る組は全部残る
  4. 式3：選んだ位置だけで状態の損失を平均する
- 選ばれなかった位置も系列には残り、後ろの予測から見える。損失から外すだけ
- 推論では PSTL は使わない
- 図4 の例（Silence×5 → Standby×3 → Response → Silence×2）：q = 1。各組から 1 個ずつ、11 個中 5 個が損失に入る
- [著者] 結果として、注釈された状態トークンの 27.5% だけを教える

## 4. データセット OneStreamer-1M

- [著者] OneStreamer-1M = 新しく作った **OneStreamer-Core** + 既存の公開データ（Streamo・JoyAI・MMDuet2・ViSpeak・StreamForest・VideoChat-OL・Seeker・VST）を掃除して共通のストリーミング形式に直したもの。合計 1,160,004 件（表6）
- これとは別に、LLaVA-Video のオフライン動画データも混ぜる（§5）
- 実際に読み込んだのは 991,773 件、詰めた後の系列は 150,261 本（表7）。元データごとの抽出の割合は書かれていない
- 汚染の除去：評価ベンチと同じ元動画を使う学習データは、区間が重ならなくても全部除いた（付録B.1）

### 4 つの族（表6、表5、付録B.1）

| 族 | 件数（うち Core） | 何を教えるか | 制御トークン |
|---|---:|---|---|
| Proactive Caption Memory | 60,000（全部 Core：階層 52,500・平ら 7,500） | 記録づくり | Silence・Observe・Summary、最後に全体の要約の Response |
| Proactive Interaction | 271,570（7,941） | 1 つの指示に何度も答える（数え上げ・連続した説明・リマインドなど） | Silence・Response（Standby なし） |
| Proactive QA | 197,584（47,683） | 先に来た質問に、答えられる時刻で 1 回答える | Silence・Standby・Response |
| Perception & Memory QA | 630,850（156,996） | オンラインの知覚と記憶の QA（一般・空間・時間・数え上げ・未来予測・手順など） | **表5 に載っていない（書かれていない）** |

- 学習の手順は 4 族とも同じ（同じ SFT、同じ損失）。違うのは系列の中身と PSTL のアンカーだけ
- Perception & Memory QA は記録づくりではない。系列の形（その場で答える普通の QA か、Silence → Standby → Response の形か）は書かれていない
- 答えの形式（多肢選択か自由記述か）は、どの族も書かれていない

### 族ごとの系列の例

- **Proactive Caption Memory**（図8 の料理動画）：89 秒 `</Observe> [89s] The cohesive dough ball rests on a white plate…`、106 秒ごろ `</Summary> [89s-106s] …`、ほかの秒は `</Silence>`。映像が終わったらユーザーの「全体を要約して」→ `</Response>` + 動画全体の説明（付録B.2）
- **Proactive Interaction**（図6 下段の数え上げ）：最初に指示 → `</Silence>` … `</Response> 1 time` … `</Response> 2 times` … `</Response> 3 times`
- **Proactive QA**（図11 の 3 段目）：最初に質問 → 00:19〜00:23 `</Silence>` → 00:24・00:25 `</Standby>` → 00:26 `</Response> The dough is shaped into a ring.`
- **Perception & Memory QA**：形は書かれていない。[AI] 「質問の時刻までの映像 → 質問 → 答え」の可能性が高い

※ 図6・図11 は推論の結果の図。学習データも同じ形だと読める

## 5. データの作り方（図5、§4、付録B.2・B.3）

図5 の上下で作るのは **Core だけ**。既存データの分はどちらも通らず、公開データを共通の形式に直したもの（具体的な手順は書かれていない）。

### 上（01〜03）：記録のデータ

1. 動画を選ぶ：変化が多く、出来事がはっきりした動画。画質が悪い・静止が長い・暗転・カットが多すぎるものは除く
2. 3 段の注釈：Gemini3.1Pro と Seed2.1Pro に、時刻付きで「短い区間の細かい説明」「出来事のまとまりの説明」「動画全体の説明」を書かせる。動画と照らして、根拠がない・時刻がずれた・段どうしで食い違うものは捨てる
3. 系列にする：短い区間の説明は区間が終わった時刻に `</Observe>`、まとまりの説明はまとまりが終わった時刻に `</Summary>`、全体の説明は最後の「全体を要約して」への `</Response>`

### 下（04〜06）：QA のデータ

- [著者] 動機：既存データは答える時刻がずれている。早すぎると言語の先入観で答えて幻覚が増え、証拠区間の終わりまで待つと遅すぎる。「証拠が足りる範囲で、できるだけ早く」答えさせる
1. QA を作る：上で確かめた記録の注釈と既存データの注釈を材料に、能力ごと（状態の追跡、行動の予測、リマインド、数え上げなど）の型で Gemini・Seed に作らせる
2. 証拠区間をおおまかに決める：Gemini・Seed に区間を出させ、その区間の映像だけを Qwen3.5-397B-A17B に見せる。正しく答えられなければ捨てる
3. 答える時刻を細かく決める：区間内の 1 秒ごとの候補時刻で、直前の映像から「答えられそうか」を点数にする
   - 推論系：Qwen3.5-9B が正解文を出す確率（直前 4 秒）
   - 知覚系：WeMM-Embedding-9B による、出来事の文と直前 2 秒の映像の近さ
   - 直前 2 つまでとの中央値でならし、最高点から 0.04 以内で一番早い時刻を選ぶ。その時刻までの映像で Qwen3.5-9B が答えられなければ捨てる
   - [実験] 元の注釈より平均 13.72 秒早まり、86.62% が早まった
4. 系列にする：証拠が出る前は `</Silence>`、出始めたら `</Standby>`、決めた時刻に `</Response>`

### 族と上下の対応

| 族 | 上か下か | 確かさ |
|---|---|---|
| Proactive Caption Memory | 上 | 確か（§4.1、付録B.1） |
| Proactive QA | 下 | ほぼ確か（最後の形が同じ。ただし明記した文はない） |
| Proactive Interaction | 書かれていない | [AI] 数え上げは下の可能性（付録B.3 の対象に「能動的な数え上げ」） |
| Perception & Memory QA | 書かれていない | [AI] 下の可能性はある（付録B.3 の対象に「状態の追跡・行動の予測」） |

- 上下は完全に別ではない。下は上で作った注釈を材料に使う（付録B.3、図5 の 04）

## 6. 学習とデータの効果（実験）

- **PSTL**（表3。ProactiveVQA / OmniMMI / OVO-Timing）

  | 状態の損失の取り方 | 教える割合 | ProactiveVQA | OmniMMI | OVO-Timing |
  |---|---:|---:|---:|---:|
  | 全部（普通の CE） | 100% | 26.1 | 30.8 | 1.5 |
  | 全部（Focal、Streamo の方法） | 100% | 47.0 | 32.8 | 26.5 |
  | ランダムに間引く | 27.5% | 26.6 | 27.4 | 1.4 |
  | 切り替わりだけ | 18.1% | 46.7 | 27.4 | 15.3 |
  | **PSTL** | 27.5% | **48.7** | **36.6** | **41.6** |

  - [著者] 減らすこと自体ではなく、何を残すかが効く。状態が続く所も教える必要がある
  - 比較は待ち受けるベンチだけ。記録づくりへの PSTL の効果は測っていない
- **記録のデータ 60K を抜いたモデル**（付録E.1）
  - 記録を使ったときの伸び（表17）：OneStreamer は OVO-Bench +2.0・StreamingBench +0.6、抜いたモデルは −0.1・+0.3。[著者] 指示で書かせるだけでは記録は効かず、書き方の学習が要る
  - 映像だけの評価でも、抜いたモデルは 6 設定すべてで 0.1〜1.1 点低い（表16）
- **データを段階的に足した比較**（付録E.4、表20）：平均 49.8 → 52.1 → 53.4 → 55.6 → 56.0。答える時刻の補正（CQTC、件数は増やさない）で OVO-Timing が 33.0 → 42.0

## 7. 書かれていないこと

1. 文の損失と状態の損失の足し合わせ方（重み）
2. 入力側（映像・質問）に損失を付けるか
3. どのタスクの系列かをモデルにどう伝えるか（学習データの指示文・システムプロンプト）
4. 族ごとの混ぜ方、元データごとの抽出の割合、LLaVA-Video の量
5. 「記録を書いた後に来た質問に、記録で答える」形の学習データ。評価の A の回答の形（記録 + 直近 16 枚 + 質問 → 制御トークンなしで答える）の学習データ
6. Perception & Memory QA の系列の形、答えの形式（多肢選択か）
7. 既存データを共通の形式に直す手順（制御トークンや時刻を付け直したか）
8. Interaction・Perception & Memory QA の Core を図5 のどちらで作ったか
9. 平らなキャプション（7,500 件）の作り方
10. Standby をどこから付けるか、Response の後も系列が続くか
11. 系列の最初の制御トークンや、q = 0 の系列の PSTL の扱い。記録の系列の最後の Response の PSTL での扱い
12. 学習の系列を窓（32 秒など）で切っているか（推論コードは 32 秒で切る）
