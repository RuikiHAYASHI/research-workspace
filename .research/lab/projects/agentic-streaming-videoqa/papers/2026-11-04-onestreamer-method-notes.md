## 1. 一言でいうと

**ストリーミング動画を見ながら、自分で「何が起きたか」の短い文を書き溜め、質問には「書き溜めた文 + 直近の数秒の映像」で答える 1 つのモデル**。いつ書くか・いつ黙るか・いつ答えるかも、同じモデルが特別なトークン（制御トークン）を出して決める。

### 論文の主張（§1・§6）

1. **PHCM**（Proactive Hierarchical Caption Memory）: 見た内容を、時刻付きのテキストに 2 段階の粒度で書き残す。細かい記述（`</Observe>`）と、終わった出来事のまとめ（`</Summary>`）。映像が窓から消えても文は残るので、昔のことに答えられる。しかも直近の映像はそのまま見るので、今の知覚は落ちない（表2）
2. **PSTL**（Proactive State Transition Learning）: 「黙る」ラベルが大量にあって学習がそれに引っ張られる問題を、学習に使う制御トークンを選び直すことで和らげる。制御トークンの 27.5% だけ学習に使って、全部使うより良い（表3）
3. **データ合成パイプラインと OneStreamer-1M**: 出力の中身と出すタイミングを「その時点で見えている証拠」に合わせた学習データを作る。既存データと合わせて約 116 万件（表6）
4. 4B モデルで 8 ベンチすべてで比較手法中 1 位（表1）

### AI の解釈（論文の主張とは分けて読むこと）

- 仕組みの核は単純。「動画の説明文（キャプション）を逐次書かせ、それを次の入力に足す」こと自体は以前からある（§2.2 でも streaming captioning・continuous commentary を挙げている）。新しいのは、**書く・黙る・答えるを 1 つのモデルの次トークン予測に統一し、そのための学習データを大規模に作った**点だと読める（推測）
- 「記憶を書くとき質問を知らない（query-independent）」ことを強く打ち出している。記憶は質問に合わせて選ばない。この点は林さんの「予習（質問の傾向をつかむ）」の方向とちょうど逆である（推測）
- 表2 の効果の大部分は OVO-Bench Backward の ASI（63.5→71.6）から来ている。Real-Time の伸びは小さい（80.9→81.4、86.3→86.9）。「記憶で知覚も良くなる」という主張は、差が小さいので慎重に読むべき（推測）

## 2. 入力から回答までの流れ

### 2.1 部品（§3.1・図3）

- **Vision encoder（映像を数値の列＝視覚トークンに変える部分）+ projector（それを LLM が読める形に変換する層）+ LLM**。初期値は Qwen3-VL-4B-Instruct（§5 Implementation Details）
- **Recent-N FIFO 窓**: 直近 N フレーム分の視覚トークンだけ持つ。古いものから捨てる（FIFO = 先入れ先出し）
- **テキスト履歴**: これまでに書いた記録と対話。捨てない（§3.2、付録 A.2）

### 2.2 制御トークン（§3.1・表5）

モデルは各時点でまず制御トークンを 1 つ出し、それによって続けて文を書くかが決まる。

| トークン | 意味 | 後に文が続くか | 使うタスク |
|---|---|---|---|
| `</Silence>` | 何も書かず見続ける | 続かない | 全タスク共通 |
| `</Observe>` | 細かい記録（物・動作・場面・状態の変化） | 続く | 記憶づくり |
| `</Summary>` | 終わった出来事・区間のまとめ | 続く | 記憶づくり |
| `</Standby>` | 証拠が出始めたが、まだ答えられない | 続かない | 先に質問が来る QA |
| `</Response>` | ユーザーに見せる答え | 続く | QA・対話 |

「出力の種類」は実質 3 つ: **記録を書く（Observe/Summary）**、**答える（Response）**、**待つ（Silence/Standby）**。

### 2.3 記憶の作り方・増え方・捨て方

- **作る**: 推論中、Observe か Summary を出したら、その記録文を自己回帰（1 トークンずつ）で生成する（§3.2、付録 A.2）
- **更新**: 書いた順にテキスト履歴の末尾へ追加するだけ（§3.2「appended to the text history in generation order」）。既存の記録を書き換えたり、まとめ直して古い記録を消したりする仕組みは論文に書かれていない。Summary も Observe を置き換えず、並べて足される
- **捨てる**: 論文の本文で捨てるのは**映像だけ**（FIFO 窓から外れた視覚トークン）。テキスト記録は残る。テキストが増え続けたときの扱いは本文にない
- 外部の検索器（retriever）や記憶用のエンコーダは使わない（付録 A.2）

**コードで見た実際の動き（OVO-Bench・StreamingBench の評価）**。論文の「1 本の系列」という説明と違い、**記憶づくりと回答は別々の 2 段階**になっている。

1. 記憶づくり（コード: `caption_video.py` の `VideoCaptionSession.step`、`caption_optimized.py` の `run_caption_pass`）
   - 4fps で、1 秒ごとに 1 回モデルを呼ぶ。1 回の入力 = system 指示 + 直近 32 回分（=32 秒 = 128 枚）の「映像 1 秒 + そのときの自分の出力」
   - `self.history = self.history[-self.max_rounds:]` で 32 回より古いものを丸ごと切る。つまり**記憶づくりの最中は、32 秒より古い映像だけでなく、自分が書いた古い記録も見えない**（実行ログ §7 と同じ結論）。論文 付録 A.2 の「記録は後の予測で使える」は、少なくとも記憶づくりの段では 32 秒以内に限られる
   - 出力が `</Observe>` か `</Summary>` で始まれば記録として集める。`prompts.py` の対応表では内部名が Observe→`response`、Silence→`standby`、Summary→`summary` になっていて、論文の Response/Standby とは別物なので注意
   - 記録の時刻は、モデルが文中に書く時刻ではなく、**その出力をした 1 秒区間**で保存する。Summary の開始時刻は「前の Summary の後の最初の Observe の時刻」（`SegmentScopeTracker.parse_online`）
   - 質問時刻で最後の出力が Observe だったら、`<STREAM_END>` を送って Summary を 1 つ出させる（`finalize_caption_boundary`）
2. 回答（コード: `local_runner.py` の `infer`、`engine.py` の `answer`、`memory.py` の `MemoryBank.render_with_budget`）
   - 新しい会話として、「記憶テキスト（Summary 一覧 → Observe 一覧の順、各行 `[開始s-終了s] 文`）+ 直近 16 枚（1fps、元の解像度）+ 質問」を入れて 1 回生成する
   - system 指示は「記憶は不完全かもしれない。食い違ったら直近のフレームを優先」（`prompts.py` の `MEMORY_QA_SYSTEM`）
   - 記憶が 12,000 トークンを超えたときだけ選別する。Summary を新しい順に優先し、Observe は**質問の単語との重なり**・新しさ・等間隔の目印で順位をつけて入るだけ入れる（`_rank_captions`）。この選別だけは質問に依存する。論文には書かれていない

### 2.4 具体例（**架空**の 60 秒の料理動画で通す）

設定: 架空の動画。0〜20 秒 卵を 2 個割る、20〜40 秒 泡立て器で混ぜる、40〜60 秒 フライパンに流す。出力文も架空。

**(A) 後から質問が来る場合（Memory QA。図2 の左）**

| 時刻 | モデルの出力（架空） | 何が起きたか |
|---|---|---|
| 0〜3 秒 | `</Silence>` | まだ書くことがない |
| 4 秒 | `</Observe> [3.0 seconds] 白いボウルの横に卵が 2 個ある` | 記録 1 |
| 9 秒 | `</Observe> [6.0 - 9.0 seconds] 1 個目の卵をボウルの縁で割る` | 記録 2 |
| 10〜19 秒 | `</Silence>` / `</Observe>`… | 2 個目を割る記録など |
| 21 秒 | `</Summary> [0.0 - 20.0 seconds] 卵を 2 個ボウルに割り入れた` | 区間が終わったのでまとめ |
| 22〜59 秒 | 同様に Observe・Summary を足す | |
| 60 秒 | 質問「最初にボウルに入れたものは？」 | |

60 秒時点で答えるときに見るもの:
- 直近 16 枚 = 45〜60 秒のフライパンの場面だけ。卵を割る場面はもう映像にない
- 記憶テキスト: Summary「[0-20] 卵を 2 個ボウルに割り入れた」、Observe「[6-9] 1 個目の卵を…」など
- → 記憶から「卵」と答えられる。これが表2 の ASI が上がる仕組み（図6 上段の「黄色い机」の例も同じ）

**(B) 先に質問が来る場合（Proactive QA。図2 の右）**

ユーザーが 0 秒で「泡立て始めたら教えて」と言う。

| 時刻 | 出力（架空） |
|---|---|
| 0〜18 秒 | `</Silence>`（証拠がない） |
| 19 秒 | `</Standby>`（泡立て器が画面に入った。まだ混ぜていない） |
| 21 秒 | `</Response> 泡立て始めました` |

数を数えるタスク（図6 下段、図11）では、1 つの指示に対して Silence を挟みながら Response を何度も出す。

**AI の注意**: 論文は (A) の記録と (B) の応答を 1 本の系列で同時に扱えるように書いているが、評価コードで確認したのは (A) の 2 段階版だけ。(B) の評価で記録も同時に書いているかは確かめていない（§7 参照）。

## 3. 流れの図

```text
 映像ストリーム（1 秒ごとに新しいフレームが届く）
   │
   ▼
 Vision encoder ─ projector ─┐
                             ▼
              ┌──────────────────────────────┐
              │ Recent-N 窓（直近の映像だけ） │ ← 古い映像は捨てる（FIFO）
              └──────────────────────────────┘
                             │  交互に並べる
              ┌──────────────────────────────┐
              │ テキスト履歴                   │
              │  [0-20s] Summary: 卵を割った   │ ← 書いた記録は残す
              │  [6-9s]  Observe: 1個目を…    │
              │  対話（質問・過去の答え）      │
              └──────────────────────────────┘
                             │
                             ▼
                    LLM（Qwen3-VL-4B 由来）
                             │ まず制御トークンを 1 つ出す
        ┌──────────┬─────────┼──────────┬───────────┐
        ▼          ▼         ▼          ▼           ▼
   </Silence>  </Observe> </Summary> </Standby>  </Response>
   何もしない   細かい記録  区間のまとめ  待機       答えを書く
                 │          │                      │
                 └────┬─────┘                      ▼
                      ▼                         ユーザーへ
            テキスト履歴の末尾に追加

 [評価コードでの実際: OVO-Bench / StreamingBench]
   段1 記憶づくり: 4fps・1秒ごと、入力は直近32秒（映像+自分の出力）だけ
   段2 回答     : 記憶テキスト全部(12k token超で選別) + 直近16枚(1fps) + 質問
```

## 4. 学習

### 4.1 学習の段取り（§5 Implementation Details、付録 C.1・表7）

- Qwen3-VL-4B-Instruct から始め、**SFT（教師ありの追加学習）を 1 段だけ**。強化学習はない
- Vision encoder は凍結。projector と LLM を学習
- データ: OneStreamer-1M + LLaVA-Video から取ったオフライン動画データ。読み込み 991,773 件を 150,261 本の系列に詰めて（packing）学習
- 1 epoch（1,174 step）、最大 131,072 トークン、学習率 1e-5（cosine）、H200 32 枚
- フレームはデータごとに 1〜4fps、最大 2,048 枚
- 制御トークン（Response・Summary など）はトークナイザに登録済みの状態から始める（付録 C.1）
- 学習コードは公開されていない（実行ログ §7）

### 4.2 損失と PSTL（§3.3、式1〜3、図4、付録 A.1）

- 文（記録・答え）のトークンは普通の次トークン予測で全部学習する
- 制御トークンだけ、どれを損失に入れるかを PSTL で選ぶ
  - 「出力アンカー」= 文を書き始める制御トークン（記憶づくりなら Observe・Summary、QA なら Response。表5）
  - 1 本の系列の中で、直前の制御トークン → 今の制御トークンの組（例: Silence→Silence、Silence→Observe）ごとに数える
  - アンカーへ入る組の中で一番多い数を上限 q にする（式1）。どの組からも最大 q 個までランダムに選ぶ（式2）
  - 例（架空）: 1 本の系列で Silence→Silence が 200 個、Silence→Observe が 10 個、Observe→Silence が 10 個なら q = 10。Silence→Silence は 200 個中 10 個だけ損失に入る
  - 選ばれなかったトークンも系列には残る。損失から外すだけ（式3）
- 推論時は PSTL を使わない。モデルがそのまま制御トークンを出す（§3.3 末尾）
- 比較（表3、ProactiveVQA の値）: 全部 CE で学習 → 26.1、全部 focal（Streamo の、頻度で重みを付ける損失）→ 47.0、同じ割合でランダム → 26.6、切り替わりだけ → 46.7、PSTL → 48.7。「減らしたから良い」のではなく「何を残すか」が効いている、という主張

### 4.3 データの作り方（§4、図5、付録 B）

**キャプション（記憶づくり）の枝**（§4.1、付録 B.2、図7〜9）

1. 動画を選ぶ: 変化が多く、出来事がはっきりした動画（YouTube 収集）。静止が長い・暗転・カットが多すぎるものは除く
2. 3 段の粒度で注釈: Gemini 3.1 Pro と Seed 2.1 Pro に、時刻付きで フレーム/クリップ・区間・動画全体 の説明を書かせる。動画と照らして、根拠のないものや時刻がずれたものは捨てる
3. ストリーミング系列に変換:
   - フレーム/クリップの説明 → その区間が**終わった時刻**に `</Observe>` の答えとして置く
   - 区間の説明 → 区間が**終わった時刻**に `</Summary>` として置く
   - 動画全体の説明 → 動画の最後に「全体を要約して」という指示を足し、`</Response>` の答えにする（記憶には入れない）
   - 要点: **見終わる前の内容を書かせない**。これが「causal（因果的）」の意味

**QA の枝**（§4.2、付録 B.3）

1. 能力ごとの型（状態の追跡、行動の予測、リマインド、数える など）を決め、キャプション注釈や既存データの注釈を材料に Gemini・Seed に QA を作らせる
2. 証拠のある区間をおおまかに特定: 動画・質問・正解を渡して区間を出させ、**その区間だけ**を Qwen3.5-397B-A17B に見せて正解できなければ捨てる
3. 答える時刻を細かく決める（区間内を 1 秒刻みで、各候補時刻の**直前**の映像を 4fps で見る）
   - 推論系の QA: 直前 4 秒を見せた Qwen3.5-9B が正解文を出す確率（トークン確率の幾何平均）
   - 知覚系: 直前 2 秒の映像と目標の出来事の文を WeMM-Embedding-9B で埋め込み、cosine 類似度
   - 直近 3 個の中央値で平らにし、最大値から 0.04 以内に入る**最も早い**時刻を選ぶ
   - 最後に、その時刻までの映像だけで Qwen3.5-9B が答えられなければ捨てる
   - 結果: 元の注釈より平均 13.72 秒早くなり、86.62% の件が早まった
4. 系列にする: 証拠が出る前は Silence、出始めたら Standby、決めた時刻に Response

**データ全体**（表6、付録 B.1）: 4 つの族、合計 1,160,004 件

| 族 | 件数 | 中身の例 |
|---|---|---|
| Proactive Caption Memory | 60,000 | 階層キャプション 52,500、平らなキャプション 7,500（すべて新作） |
| Proactive Interaction | 271,570 | 実況、通知、数える など（Streamo・JoyAI 等の既存データが多い） |
| Proactive QA | 197,584 | 先に質問が来る QA |
| Perception & Memory QA | 630,850 | 普通の QA。最大は StreamForest 由来の Spatial QA 337,570 |

- ベンチのテスト動画と同じ元動画を使う学習データは、別の区間でも全部除いた（付録 B.1）
- 段階的に足した比較（表20）: 中身の検証と時刻の補正（CQTC）だけで OVO-Timing が 33.0→42.0 と一番大きく伸びた
- 記憶づくり用の 60K を抜いたモデルは、記憶を使っても FIFO とほぼ同じ（OVO-Bench −0.1、表17）。「プロンプトで書かせるだけでは効かず、学習が要る」という主張の根拠

## 5. OneStreamer の「記憶」は記録（レコード）か記憶（メモリ）か

研究室の整理（2026-10-30 MTG）: 記録されたもの（コード化されたもの）はレコード、人間の頭の中にあるものはメモリ。従来研究の「メモリ」はレコードに近い。

**結論: OneStreamer の「記憶」はレコードに近い。** 根拠:

1. **中身が外に書き出された文そのもの**。時刻付きの自然言語の文で、人が読める（§3.2、図7〜10）。コードでも `MemoryEvent(kind, start, end, text)` の一覧で、回答時に `[開始s-終了s] 文` の行に並べるだけ（`memory.py` の `MemoryBank.render`）
2. **追記だけで、書き換えない**。生成順に末尾へ足す（§3.2）。後の証拠で前の記録を直す仕組みはない。論文自身も、誤った記述を後で直さない失敗例を挙げている（付録 F.3・図12、プリンタを「閉じる」と誤って書き、開いた状態が見えても訂正しない。ただしこれは Response の例で、記録ではない）
3. **質問と無関係に書く**（query-independent、§3.2）。使う時に質問で解釈し直す。「書く」と「読む」が分かれていて、帳簿や日誌の形に近い
4. **モデルの重みの中ではなく、入力の文脈に置かれる**。毎回テキストとして読み直す。人間の記憶のように、使うほど強まる・忘れる・連想でつながる、という性質はない

メモリ寄りに見える点（AI の解釈、推測）:
- Summary は、細かい記録を「出来事」の単位にまとめ直す。何を残すかを学習した方針で選ぶ（全部は書かない。360 秒の例で Observe 26 件・Summary 2 件、付録 E.3）。「選んで書く」のは記憶に似た面がある
- 学習の効果として、記録を書く練習が視覚の理解そのものも良くした、と主張している（表16: 記憶を使わずに評価しても、60K を抜いたモデルより少し高い）。これは重みの側に残る効果で、レコードではない。ただし差は 0.1〜1.1 点と小さい
- それでも、「後で使うための情報」本体はあくまで書かれた文であり、レコードに分類するのが妥当（推測）

## 7. 分からなかったこと・論文に書いていないこと

推測で埋めず、ここに残す。

1. **テキスト記憶が増え続けたときの扱い**。論文の本文には上限・削除・圧縮の話がない。評価コードでは回答時に 12,000 トークンを超えると質問の単語で選別する（`memory.py` の `render_with_budget`）。これは論文の「質問と無関係」という説明と少し食い違う
2. **記憶づくりのとき、古い記録が見えるか**。論文（§3.2・付録 A.2）は「記録は後の予測で使える」と書くが、評価コード（OVO-Bench・StreamingBench）では記憶づくりの入力が直近 32 秒に切られ、それより古い自分の記録も消える。学習時の系列ではどうだったか（学習の最大長 131,072 トークンの中で全部見えていたのか）は書いていない
3. **論文の「1 本の系列」と評価コードの「2 段階」の違い**。表2 の PHCM（Recent-16 + 記憶）は、記憶づくりは 128 枚（4fps）、回答は 16 枚（1fps）という別設定（付録 D「Evaluation settings」）。1 本の系列のままで回答する場合の性能は示されていない
4. **Proactive 系ベンチ（ProactiveVQA・OmniMMI・OVO-Timing・ViSpeak）で PHCM の記録を同時に書いているか**。付録 D の設定には窓の枚数しか書いておらず、記録の有無が分からない。コードも今回は確かめていない
5. **Summary を出す区間の境目はどう決まるか**。学習データでは注釈の区間の終わり（§4.1）。推論ではモデル任せで、境目の決め方や長さの目安は書いていない
6. **Standby の学習データの作り方の細部**。「証拠が出始めたら Standby」とあるが（§4.2）、証拠区間の始まりから補正後の答える時刻までを全部 Standby にするのか、は明記がない
7. **記録の誤り（幻覚）の割合**。記録文がどれくらい正しいかを測った結果はない。失敗例は Response の 1 件（図12）だけ
8. **OVO-Timing の評価がサンプリング（温度 0.7 など）であること**は論文に書いていない（実行ログ §7。コードで確認済み）。他のベンチは貪欲法（付録 C.2）
