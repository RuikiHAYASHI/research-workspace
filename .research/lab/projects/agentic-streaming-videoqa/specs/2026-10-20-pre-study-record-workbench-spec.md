# 記録Agent v3 Workbench（新リポジトリ）spec

## 1. 目的

ブラウザで選んだLongVideoBenchの動画1本に対して、イベント記録Agent（プロンプトv3）を先頭から最後まで実行し、ターンごとに「サンプリングした画像列」と「Markdownの記録」を並べて確認できる状態を、新しいリポジトリで作る。

ブラウザで動かす目的は、**プロンプトがうまく働いているかを監視すること**（2026-10-20 決定）。正答率の評価は対象外。

ゴール: 新リポジトリに環境構築・インストール手順を用意し、このマシンで実際にQwen3-VLを動かして、ブラウザから1本の動画の推論を最後まで終えられること。

## 2. 前提と決定事項

元の決定は source_brainstorm の2つのメモにある。

- 記録は「索引」。1区間につき1回の呼び出しで、SCENE・ENTITY・OBJECT・EVENT・CHANGE・TEXTを1行1事実で出力させる。
- 前の区間の記録はモデルに見せない。区間ごとに独立。
- 予習は手書きのプロンプト（v3）で代用する。
- 回答と集約は今回は作らない（2026-10-20 決定「回答，集約は一旦置きます」）。
- 区間の既定値は20秒・8枚。`max_new_tokens` は大きく（4096）し、token数を記録する。
- 区間の端で動作が続いているかは、コードで判定する。
- 旧Workbenchの「データセット＋動画・質問の選択画面」は気に入っているので残す。実行画面は作り直す。
- コミットは小さな単位で、日本語で詳しく書く。

## 3. 採用する内容

### 3.1 リポジトリの作り方

- 旧Workbench `main`（`65af089`）のファイル一式を、新リポジトリの最初のコミットとして取り込む（履歴は引き継がない。コミットメッセージに取り込み元のcommitを書く）。
- `.env`、`.venv`、`.runtime`、`outputs/` は取り込まない。
- その後の変更は、小さなコミットに分けて積む。
- 作業場所: `/mnt/HDD10TB-2/hayashi/2026_10_hayashi_pre_study_agent_system_workbench`
- パッケージ名・CLI名は旧Workbenchと同じ（`longvideoqa_workbench`、`longvideoqa`）のまま使う。名前の変更は今回の要求にないため行わない。

### 3.2 推論の流れ（Situation／Summary／Answer → 記録Agentだけ）

- Agentは `record` の1種類だけにする。ウィンドウごとに1回呼び、EOFで終了する。Summary Agent、Answer Agent、EOF後の回答、正誤判定は削除する。
- 記録はどの質問にも依存しない。プロンプトに質問文・選択肢を入れない。質問の選択は「どの動画か」を決めるためと、画面での参照のためにだけ使う。
- 既定のプロンプトは v3（`2026-10-20-event-log-prompt-v3.md` の本文）。prompt_id は `record.image.v3`。
- frame一覧（`{{chunk.frame_manifest}}`）は、モデルが時刻を写しやすいように1行1枚の形式にする（例: `frame 1: 120.0 s`）。時刻は小数1桁。
- 既定値: `window_seconds: 20`、`frames_per_window: 8`、`visual_input_mode: image_list`、`reader_mode: target_only`、`max_new_tokens: 4096`、`temperature: 0.0`、モデル `Qwen/Qwen3-VL-4B-Instruct`。
  - image_list を既定にする理由: v3は「frameは別々の画像として渡される」前提で設計した。video_clip は開発者設定から選べるまま残す。
- 推論開始後は、ブラウザ側の操作なしでEOFまで自動で進める（旧Workbenchの「ターンごとにボタンを押す」方式はやめる）。キャンセルはできる。

### 3.3 出力の解析と区間の端の判定

- モデル出力を1行ずつ解析する。形式 `- [start-end] TYPE: description`。
- 解析できない行は捨てずに「解析できなかった行」として残す。解析の失敗で推論を止めない。
- 各行について、コードで次を付ける（許容誤差0.05秒）:
  - `from_window_start`: start がそのウィンドウの最初のframeの時刻と一致する
  - `to_window_end`: end が最後のframeの時刻と一致する
  - `time_in_frame_list`: start と end が両方ともframe一覧の時刻に含まれる（含まれなければ「時刻がframeと一致しない」と表示）
- 区間をまたいでつなぐ処理（集約）は作らない。

### 3.4 保存するもの（Run artifact）

`<OUTPUT_ROOT>/<run-id>/` に次を保存する。

- `result.json`: 設定、プロンプト本文、動画・質問の情報、ウィンドウごとの結果（frameの時刻と画像path、モデル生出力、解析した行、境界の印、入力token数、生成token数、上限に達したか、生成時間）、状態。
- `record.md`: 動画全体の記録。ウィンドウ順に、解析した行をそのまま並べたMarkdown。
- `frames/`: サンプリングしたframeのJPEG。

旧形式（Record v2、Legacy、v3のSituation/Summary）のrunを読む機能は削除する。新リポジトリには旧runがないため。

### 3.5 ブラウザ画面

- **データセット・動画・質問の選択画面**: 旧画面を基本そのまま使う。次を追加する。
  - 動画一覧の各動画に、その動画の質問のタスクのタグ（例: `SSS` `E3E`）を表示する。T系（字幕起点）のタグは区別できる色にする。
  - 質問の一覧にも、各質問のタスクのタグを表示する。
  - 検索でタスクのタグを指定して絞り込めるようにする（検索語に略号を入れると一致する、またはタグの選択欄）。
- **推論前の設定画面**: 記録Agentに合わせて作り直す。表示・設定する項目:
  - 選んだ動画（長さ、ジャンル）と、その動画の質問（タグ付き、参照用）
  - 区間の長さ、区間あたりの枚数、予想ターン数
  - モデル、`max_new_tokens`、temperature
  - プロンプト（記録Agent用。Prompt Libraryから選ぶ・確認する）
  - 開発者用: 映像入力の方式、読取方式
  - 配置は、左に設定、右に動画・質問・プロンプトの確認、とし、旧画面より余白と文字の大きさを整える。
- **実行中**: 進み具合のゲージ（完了ターン数／予想ターン数、経過時間、残り時間の目安）。ターンの中身は表示しない。
- **実行後の結果画面**: ターンごとに切り替えて見る。
  - そのターンのframe画像列（時刻付き）
  - そのターンの記録（TYPEごとに色分けした行の一覧。境界の印、時刻がframeと一致しない行の警告、解析できなかった行）
  - そのターンのtoken数・上限到達・生成時間
  - モデル生出力とプロンプト（詳細として開く）
  - 動画全体の `record.md` を開ける
- 保存済みのrunは、サーバーを再起動した後もブラウザで開ける（旧Workbenchと同じ）。

### 3.6 既知の不具合2件

原因を調べてから修正する。原因と修正内容は実装時に本specの「8. 実装記録」へ書く。

1. 実行するたびに、動画一覧のプレビューの高速化が外れる。
2. 名前を変えた（rename）動画が、元の名前に戻る。

それぞれ、再現するテストまたは手順を作り、修正後に直っていることを確かめる。

### 3.7 環境構築

- `uv` で、リポジトリ直下に `.venv`（Python 3.12）を作る手順と、それを行うスクリプト `scripts/setup.sh` を用意する。
- 依存: 旧環境で動いている組み合わせ（torch 2.14 + CUDA 13.0、transformers 5.x、accelerate、av、numpy、Pillow、PyYAML、pytest）。`sequential_loader` は、ローカルのリポジトリ（既定 `../sequential_loader`、環境変数で変更可）からeditableでinstallする。
- `.env.example` と README に、`LVB_ROOT`、`CUDA_VISIBLE_DEVICES`、`PORT`、`WORKBENCH_HOME`、`OUTPUT_ROOT` の設定方法、起動方法、preflightを書く。

## 4. 対象外

- 回答Agent、集約Agent、正答率の計算
- 複数動画の一括実行（旧 `batch-run`）と、Answerの再実行（旧 `answer-replay`）。今回は削除し、必要になったら作り直す
- 字幕の入力
- 予習Agent
- 旧形式のrunの読込み
- Video-MME などLongVideoBench以外のデータセットの追加

## 5. 互換性

- 旧Workbenchリポジトリは変更しない。
- 新リポジトリの設定ファイル・run artifactは、旧Workbenchと互換にしない（Agentの構成が変わるため）。
- ブラウザのライブラリ（別名・お気に入り・フォルダ）の保存場所（`WORKBENCH_HOME`）の既定値は、旧Workbenchと共有しない名前にする（旧データを壊さないため）。旧データの取り込みは行わない。

### 8.2 不具合の原因と修正

1. **プレビューが遅くなる**: cacheは消えていなかった。原因は、thumbnail・previewを1回返すたびに、LongVideoBenchの動画一覧（753本すべての `resolve()` と `is_file()`）を2回作り直し、索引のsignatureも全動画分計算し直していたこと。さらにthumbnailを `no-store` で返していたので、一覧を描き直すたびに全カードの画像を取り直していた。推論は同じサーバープロセスのスレッドで動くため、実行中・実行後はCPUを取り合ってさらに遅くなったと考えられる（GPU実行中の計測はしていない）。一覧を最初の1回だけ作る、同じ一覧なら索引を作り直さない、thumbnailをブラウザでcacheできるようにする、の3点で修正した。プレビュー1回あたりの前処理は約0.15秒から約0.0001秒になった（実データで計測）。
2. **名前が元に戻る**: 別名の保存処理は正しく動いていた。このマシンの保存先には別名が一度も保存されておらず（お気に入りだけ）、10/01頃に `/tmp` を保存先にしていた時期の別名がマシン再起動で消えた可能性がある。コード上の問題は、(a) 推論画面が元のIDだけを見出しに出していた、(b) 名前変更後の一覧の再取得が別の操作と重なると古い名前のまま残る、の2つだった。どちらも修正した。**林が見ていた「元の名前」がどの画面だったかは未確認**。

### 8.3 実装時に決めたこと（non-blocking）

- 既定の映像入力は `image_list`（v3は「frameが別々の画像として渡される」前提で設計したため）。`video_clip` 用にも同じ本文の `record.video.v3` を置いた。
- frame一覧は「frame 1: 120.0 s」の1行1枚、時刻は小数1桁。区間の端の判定はこの表記と比べ、許容誤差0.05秒。
- 解析できない行は捨てずに残し、推論は止めない。
- `max_new_tokens` は4096。入力token数・生成token数・上限到達・生成時間をターンごとに保存する。
- 旧画面の「設定を呼び出す」「テンプレート保存」はUIから外した（APIは残っている）。
