# 新規リポジトリで作る、対話的な逐次動画質問応答システム 実装仕様

## 位置付けと今回の到達点

本書は、既存の フレーム単位の文章記憶（frame-level text memory） を改修する計画ではない。新しいリポジトリに、動画を先頭から順に扱う動画質問応答システムを環境構築から作るための正本である。過去の関連仕様にある 50Salads と `sequential_loader` を初期実装の前提から外し、本書では LongVideoBench の実データを最初の対象にする。

今週の到達点は、ブラウザで設定と各処理段階の指示文を確認・変更し、LongVideoBench の実在する1動画・1問を、区間ごとに順次処理して最終回答まで到達できる最小システムを作ることである。精度比較、全件評価、既存方式との優劣の主張は含めない。

## 用語

| 用語 | 説明 |
| --- | --- |
| 接続部（adapter） | データセットやモデルごとのファイル形式・呼出し方法の違いを、システム内の共通形式に変換する部品。 |
| 実行設定 | 使用データ、動画、質問、モデル、区間、指示文、生成設定を一回の実行に固定する保存可能な設定。 |
| 区間 | 動画を先頭から順に処理するために区切った時間範囲。 |
| 処理段階 | 区間理解、根拠の集約、最終回答のように順番に行う処理。 |
| 実行記録 | 一回の実行について保存する設定、入力概要、モデル出力、状態、失敗理由。 |
| 擬似モデル | 実際のモデルを読み込まず、呼出し順や保存処理を確かめるテスト用モデル。 |

## 初期データ: LongVideoBench の1動画・1問

データセットの登録先は、研究ワークスペースと同じ階層の次とする。

```text
/mnt/HDD18TB/hayashi/data/LongVideoBench
```

初期実行は validation（検証用）注釈の次の1件に固定する。動画と質問は「動画IDだけ」ではなく、`(video_id, question_id)` の組で選ぶ。同じ動画に複数質問があるためである。

| 項目 | 値 |
| --- | --- |
| 質問ID | `P9hDA0u6FO0_0` |
| 動画ID | `P9hDA0u6FO0` |
| 動画ファイル | `videos/P9hDA0u6FO0.mp4` |
| 注釈ファイル | `lvb_val.json` |
| 動画長 | 1,995.88秒（約33分16秒） |
| 質問 | `Which of the following sequences of scenes is correct?` |
| 選択肢 | 4つの場面順序候補 |
| 字幕 | 初期実行では使わない |

この質問は、動画内の離れた複数場面の出現順を比較する必要があり、約30分の逐次処理と過去根拠の集約を確認しやすい。字幕なしでも扱える。正解ラベルはモデル入力、段階ごとの指示文、中間出力に渡さない。実行後の人手確認または後続の評価だけに使う。

ローカル確認では、注釈は validation 1,337問と test 5,341問、計6,678問を含む。注釈から参照される動画は3,761本であり、`videos.tar` 内のMP4は3,991本である。したがって接続部は動画ディレクトリを列挙して対象を決めず、注釈JSONの `video_path` を正として動画を解決する。注釈が参照する動画はすべてローカルに存在することを確認済みである。

## 新規リポジトリと開始条件

### 推奨名

推奨するリポジトリ名は `2026_09_hayashi_longvideoqa_workbench` とする。ローカル配置の候補は次である。

```text
/mnt/HDD18TB/hayashi/2026_09_hayashi_longvideoqa_workbench
```

既存の `/mnt/HDD18TB/hayashi/2026_09_hayashi_streaming_video_qa` は Qwen の読み込み方などを確認するための read-only 参照先であり、変更しない。

### Step 0: ユーザーによるリポジトリ作成

ユーザーが上記名または同等の新規リポジトリを作成し、`main` に最小の初期コミットを一つ作る。初期コミットには `README.md` だけでよく、データ、動画、モデル重み、認証情報、実行出力を含めない。

ユーザーが「実装して」とともにリポジトリのローカルパスを知らせ、初期コミット済みで `main` と作業ツリーが未変更（clean） であることを示した時点で、以下の Step 1 から実装を開始する。この依頼はその条件を満たした後の実装着手を許可する。リモート（remote）への push、プルリクエスト作成、`main` へのマージは別途指示があるまで行わない。

実装開始時には、対象リポジトリ、初期コミット、作業ツリー、局所の `AGENTS.md` または `CLAUDE.md`、Pythonの利用可能版を read-only で確認する。

## 設計

### 変えない共通処理と、実行ごとに変える設定

画面から変更しない共通処理は、実行設定の検査、動画を先頭から順に処理する制御、段階ごとの記録、失敗の記録、新規実行記録の作成である。

実行ごとに画面で選択または変更できるものは、データセット接続部、登録済みデータ、動画・質問の組、モデル接続部、モデル識別子、生成設定、区間の長さ、区間内の画像の選び方と枚数、各段階の指示文である。開始時に確定した設定全体を保存し、完了済みの実行記録は変更しない。

### 接続部

| 接続部 | 責務 | 初期実装 |
| --- | --- | --- |
| データセット接続部 | 注釈と動画の形式を共通の「質問付き順序画像列」へ変換する | LongVideoBench。`lvb_val.json`、`videos/`、`(video_id, question_id)` 選択を扱う |
| モデル接続部 | 指示文、画像、生成設定を受け、生成文・元出力・モデル情報を返す | 擬似モデルと Qwen3-VL。Qwen用依存は任意導入に分離する |
| 区間分割部 | 順序画像列を、指定した長さと画像数上限で区間に分ける | 時間幅固定・区間内の時刻一様サンプリング |

接続部を追加しても逐次処理の中心を書き換えない。データセット接続部はデータの解釈だけを担い、区間の分け方は担わない。初期画面では LongVideoBench と登録済みモデルだけを選べるようにし、任意のファイルパス、任意コード、接続部ファイルのアップロードは受け付けない。

### 逐次処理の流れ

初版は任意の処理グラフを組むものではなく、次の線形処理に限定する。

```text
LongVideoBench 接続部
  -> 画像列を先頭から順に読む
  -> 区間へ分割する
  -> 区間理解（各区間で一回）
  -> 根拠の集約（有効時のみ、各区間で一回）
  -> 最終回答（動画終端で一回）
```

初期値は「区間長60秒、区間あたり時刻一様の4画像、字幕なし」とする。画面で変更でき、変更後の値を実行設定に固定する。1,995.88秒の初期動画では、既定値で34区間になる。

区間理解は、現在区間の画像・時刻と質問・選択肢だけを受け取る。根拠の集約は、現在区間の検証済み出力と過去区間までの集約結果だけを受け取る。未来の画像、未来区間、動画全体を事前に見て得た情報は渡さない。最終回答だけは動画の終端後に、過去の区間出力または最終集約結果を使える。

区間理解の保存形式は フレーム単位の文章記憶（frame-level text memory） ではない。少なくとも観測、時系列上の出来事、質問との関連根拠、不確実な点、元のモデル出力を持つ構造化出力とする。

### 指示文を画面で確認・変更する仕組み

画面は「区間理解」「根拠の集約」「最終回答」をカードとして表示する。各カードでは、使用モデルと生成設定、利用可能な入力、指示文、展開後の指示文の見本、実行後の入出力を確認・編集できる。

指示文で使える変数は `{{question}}`、`{{choices}}`、`{{chunk.start}}`、`{{chunk.end}}`、`{{chunk.frames}}`、`{{previous.evidence}}`、明示された前段出力だけに限定する。実行前に、未定義変数、未対応の画像入力、未来段階の参照、出力形式の不一致を拒否する。画面から任意の Python、シェルコマンド、任意パス、既存記録の変更・削除を許可しない。

### 保存する実行記録

各実行で `outputs/<run-id>/` を新規作成し、上書き・再開はしない。

| ファイル | 保存内容 |
| --- | --- |
| `execution_settings.json` | 確定した設定、指示文、データ・モデル・区間分割の識別子、生成設定、コード版 |
| `run_status.json` | 待機・実行中・成功・失敗、現在段階、開始終了時刻、失敗理由 |
| `chunks.jsonl` | 区間番号、時刻範囲、採用画像の番号・時刻、入力概要 |
| `stages.jsonl` | 段階、区間番号、展開済み指示文、入力概要、元出力、検証済み出力、エラー、処理時間、モデル情報 |
| `final_answer.json` | 最終回答、参照した区間または集約結果の識別子、入力のハッシュ値 |

動画画像、モデル重み、認証情報、絶対パス、正解ラベルは実行記録に保存・表示しない。保存するのはデータ登録名、動画・質問の選択子、モデル名と版、設定ハッシュ、Git commit IDである。

### ローカルサーバとブラウザ

外部のWebフレームワークを追加せず、Python標準ライブラリのHTTPサーバと、標準HTML・CSS・JavaScriptで実装する。待受先は `127.0.0.1` のみとし、外部公開しない。

| HTTP入口 | 役割 |
| --- | --- |
| `GET /` | 設定、実行、結果閲覧の画面を返す |
| `GET /api/capabilities` | 登録済み接続部、データ、モデル能力、変更可能な設定を返す |
| `POST /api/recipe/preview` | モデルを呼ばずに設定を検査し、展開指示文の見本を返す |
| `POST /api/runs` | 検査済み設定を保存し、逐次実行を開始して実行IDを返す |
| `GET /api/runs` と `GET /api/runs/<id>` | 状態と保存済み中間出力を返す |

ブラウザの定期問い合わせは状態表示だけに用いる。動画処理は一つのPythonプロセスで順に行う。複数サーバの非同期通信、ジョブキュー、任意ノード接続画面、生成途中の文字列表示は対象外である。

## 環境とデータの扱い

Python 3.12を基準に仮想環境とパッケージ定義を作る。通常の開発環境にはテストと画像読み取りの依存だけを導入し、Qwen3-VLなど実モデルの依存と重みは任意導入に分ける。データセット、動画、モデル重み、Hugging Face token、`outputs/` はリポジトリに追加・commitしない。

LongVideoBenchのデータ場所はサーバ起動時に登録名 `longvideobench` として設定する。ブラウザと実行記録は登録名だけを扱い、絶対パスを出さない。

## ブランチとコミットの規約

- 1 Stepにつき1ブランチを作る。前Stepの末尾確認が成功したHEADから次Stepのブランチを作る。
- 1小工程につき1コミットを作る。小工程用のブランチは作らない。
- Step末尾確認に失敗した場合は同じブランチで `fix:` または `test:` の修正コミットを作り、成功するまで次へ進まない。
- 各コミットの表題は日本語の完結した一文にする。本文は箇条書きにせず、「対象に変更を行った。理由は…である。検証として…を実行し、…を確認した。影響として…がないことを確認した。次は…を進める。」という日本語の段落にする。未検証なら、その理由と対象外であることを段落に明記する。
- データ、動画、モデル重み、認証情報、`outputs/` はcommitしない。push、プルリクエスト、マージは別途明示指示が必要である。

```text
main（ユーザー作成の初期コミット）
└── feat/step-01-environment
    └── feat/step-02-common-contracts
        └── feat/step-03-longvideobench-and-model-adapters
            └── feat/step-04-sequential-pipeline
                └── feat/step-05-run-records-and-command
                    └── feat/step-06-local-server
                        └── feat/step-07-browser-screen
                            └── feat/step-08-integration-verification
```

## 実装Step

### Step 1: 環境構築

**ブランチ:** `feat/step-01-environment`

1. 「Python実行環境を追加する。」というコミットで、Python 3.12、パッケージ定義、基本依存、`outputs/`などの除外設定を追加する。
2. 「基本テストを実行できるようにする。」というコミットで、テスト発見・実行とimport確認を追加する。
3. 「ローカル開発手順を記載する。」というコミットで、基本環境、任意の実モデル依存、データ等をcommitしない規則をREADMEに書く。

**末尾確認:** テスト一式、対象パッケージのcompile、環境構築手順の確認。実モデルと実データは使わない。

### Step 2: 共通データ形式と設定検査

**ブランチ:** `feat/step-02-common-contracts`

1. 「動画質問応答の共通データ形式を追加する。」というコミットで、動画、画像、区間、モデル要求・応答、処理段階、実行設定を定義する。
2. 「実行設定を検査できるようにする。」というコミットで、未登録接続部、未定義変数、段階順の不整合、画像入力不整合を実行前に拒否する。
3. 「実行設定の検査をテストする。」というコミットで、正常・異常設定を擬似接続部で確認する。

**末尾確認:** Step 1の確認、設定検査テスト、compile。

### Step 3: LongVideoBench・モデル接続部と区間分割

**ブランチ:** `feat/step-03-longvideobench-and-model-adapters`

1. 「接続部の登録機構を追加する。」というコミットで、接続部の登録、能力情報、擬似データセット、擬似モデルを追加する。
2. 「LongVideoBenchの質問単位接続部を追加する。」というコミットで、`lvb_val.json`から `(video_id, question_id)` を解決し、注釈の `video_path` により画像列を順番に返す。正解ラベルはモデル要求に含めない。
3. 「時間幅で区間を分ける機能を追加する。」というコミットで、未来を読まずに時刻範囲と採用画像情報を持つ区間を作る。
4. 「Qwen3-VL接続部を追加する。」というコミットで、共通要求から画像あり・なしの生成とモデル情報を返す。実モデルの依存がない環境では、読み込み時に明確な案内を返す。
5. 「接続部と区間境界をテストする。」というコミットで、順序、注釈起点の動画解決、未来遮断、画像数上限を確認する。

**末尾確認:** Step 2の確認、接続部と区間のテスト、compile。実モデルは使わない。

### Step 4: 逐次動画処理

**ブランチ:** `feat/step-04-sequential-pipeline`

1. 「処理段階の指示文を安全に展開する。」というコミットで、許可変数だけを展開し、未定値を明示する。
2. 「区間理解を順次実行できるようにする。」というコミットで、構造化出力と元出力を得る。
3. 「過去根拠を因果的に集約する。」というコミットで、現在区間と過去情報だけを使う任意の集約段階を追加する。
4. 「動画終端で最終回答を生成する。」というコミットで、最終段階が一回だけ実行されるようにする。
5. 「逐次処理の因果性をテストする。」というコミットで、呼出し順、未来遮断、失敗停止、最終段階一回を確認する。

**末尾確認:** 全テスト、compile、擬似2区間動画の最小実行。

### Step 5: 実行記録とコマンド

**ブランチ:** `feat/step-05-run-records-and-command`

1. 「実行設定と状態を保存する。」というコミットで、新規実行ディレクトリ、状態遷移、上書き禁止を実装する。
2. 「区間と段階の記録を保存する。」というコミットで、入力概要、出力、検証結果、失敗を逐次保存する。
3. 「動画質問応答の実行コマンドを追加する。」というコミットで、設定を受けて逐次処理を行うコマンドを追加する。
4. 「実行記録とコマンドをテストする。」というコミットで、設定不変性、途中失敗、既存実行非変更を確認する。

**末尾確認:** 全テスト、compile、`--help`、擬似接続部の実行記録確認。

### Step 6: ローカルサーバ

**ブランチ:** `feat/step-06-local-server`

1. 「選択可能な設定を取得するAPIを追加する。」というコミットで、登録済み接続部、データ、変更可能な設定を返す。
2. 「実行設定をプレビューして検査するAPIを追加する。」というコミットで、モデルを呼ばずに展開見本と検査結果を返す。
3. 「実行開始と状態取得のAPIを追加する。」というコミットで、新規実行の開始と記録済み結果の取得を行う。
4. 「ローカルサーバ境界をテストする。」というコミットで、loopback限定、不正設定、未登録データ、パストラバーサルを確認する。

**末尾確認:** 全テスト、`--help`、擬似入力によるloopback API確認。

### Step 7: ブラウザ画面

3. 「実行状態と段階出力を表示する。」というコミットで、状態、展開指示文、入力概要、元出力、検証結果、エラーを表示する。

### Step 9: Qwen3-VL実行環境とGPU固定の強制

**状態:** draft。依存導入、モデル重みの取得、GPU推論はこのStepの実装・検証を許可する明示指示があるまで行わない。

**ブランチ:** `feat/step-09-qwen-gpu-guard`

Qwen3-VLを用いるすべての実行プロセスは、必ず次の環境変数を指定して起動する。

```bash
CUDA_VISIBLE_DEVICES=2,3
```

これは推奨値や省略可能な既定値ではない。値が未指定、空、`2, 3`、`3,2`、またはその他の値である場合は、Qwen3-VLのモデル読込みを開始せず、明確な設定エラーとして失敗させる。擬似モデルだけを使う単体テストはこの制約の対象外とする。

`CUDA_VISIBLE_DEVICES=2,3` を設定したプロセスから見えるCUDA論理デバイスは `cuda:0` と `cuda:1` になる。これは物理GPU 2・3を可視化した結果であり、コードや設定で物理番号を `cuda:2`、`cuda:3` として指定してはならない。既存の `device_map="auto"` は維持し、可視化された2枚だけへ自動配置させる。

1. 「Qwen3-VLの任意依存を導入できるようにする。」というコミットで、既存の`.venv`へQwen用optional dependencyを導入する手順をREADMEと開発文書に記載する。Qwen関連プロセスを起動する例はすべて `CUDA_VISIBLE_DEVICES=2,3` を明示する。依存導入はネットワーク状態を変更する操作であり、このStepの実装指示とは別にユーザーの許可を得てから実行する。
2. 「Qwen3-VLのGPU可視性を検査する。」というコミットで、モデル読込みの最初に `CUDA_VISIBLE_DEVICES` が文字列として厳密に `2,3` であることを検査する。条件を満たさない場合は、モデル重み取得・`torch`初期化・推論を行わず、必要な環境変数を示すエラーを実行記録と画面へ返す。
3. 「Qwen3-VLのGPU固定をテストする。」というコミットで、環境変数が未設定・不一致・一致の各場合をテストする。一致の場合だけ後続の依存読込みへ進むこと、不一致の場合にモデル読込みを試行しないことを確認する。実GPUやモデル重みは使わない。

**末尾確認:** 既存の全テスト、compile、Qwen依存なしの環境における不一致値の失敗テスト。一致値での実GPU確認、依存導入、重み取得は対象外とする。
