## 要旨

3-Agent構成をSituation → Summary → Answerの単純なbaselineに整理し、LongVideoBenchの短尺・約3分動画で試行結果を報告した。Situation/Summaryの逐次処理は確認できた一方、長い実行時間、Summaryの肥大化と過去情報の脱落懸念、Answerの出力形式validation失敗が課題となった。

教授側の主な指摘は「AIが生成した設計・Prompt・結果を自分の言葉で説明し、どこに時間がかかり、なぜ失敗したのかを調べること」と「baselineを作っただけで研究の差分ではないので、既存研究との比較を始めること」。関連研究調査では、Agent系全般を漫然と読むのではなく、**過去イベントをMemoryへどう残すか**など一つの問いに絞り、代表論文のRelated Workから10〜20本程度へ展開する方針が具体的に示された。

## やったこと

### 1. 3-Agentの理解・簡略化とbaseline

前回指摘されたAgentの入出力、Prompt、実行結果を理解するため、図と具体例を整理した。元のMemory Agentはイベント台帳・根拠ID・未解決事項を含む複雑な契約だったが、初期実装の役割を単純化し、Summary Agent（要約Agent）として扱う。

| Agent | 入力の中心 | 出力 | 実行タイミング |
| --- | --- | --- | --- |
| Situation Agent | 現在chunkのサンプリング済み動画フレーム | situation_description（現在区間の状況説明） | chunkごと |
| Summary Agent | previous_summary、現在のsituation_description | summary（累積要約） | chunkごと |
| Answer Agent | Question、Choices、動画終了時のfinal summary | answer（選択肢） | EOF時に1回 |

現在のSituation / SummaryはQuestionやChoicesに依存させず、Answerで初めてQuestionを使う単純な情報の流れにする。構造化した重要イベント、Evidence参照、可否判定などはbaselineの基本契約から一度外す。これは図だけの省略ではなく、簡単な契約として実装し直した、という説明があった。

教授との確認では、**これは研究の新規手法の実証ではなく、比較・改良を始めるための土台**である点が明確になった。

## 話したこと

### 1. 実験結果の見せ方と実行時間の原因分析

- 動画長（duration）を比較表へ明示する。chunk長、sampling間隔とFPS（逆数の関係）、処理したchunk数、推論時間の意味を説明できるようにする。
- 「夜に開始し、朝見たら時間がかかっていた」では不十分。**Agentごと・chunkごとの実測時間を分解して、何がどれだけ時間を消費しているかを示す**必要がある。
- Situation Agentの平均時間だけで数時間の総所要時間を説明できない。Summary Agentの入出力が伸びる影響、token数、増減が不規則な理由などを追う。
- 結果を数値で並べるだけでなく、Promptの入力と出力例を実際に確認し、なぜその結果になったか検討する。

### 2. Agent Promptの妥当性

- 現行のSituation / Summary / AnswerのPromptは短く、やるべきこと・守るべき条件の記述が十分ではないとの指摘。
- 既存手法の論文本文やAppendixに掲載された実際のPromptを参考に、具体的な役割・制約・出力形式を検討する。Qwen3-VLのような対象モデルの特性も考慮する。
- 天野さんにPrompt設計の経験を聞く案が出た。会話中の「5〜6倍」は不足感の表現であり、Promptの長さを機械的に5〜6倍にすることが決定されたわけではない。

### 3. Answer Agentが回答形式を守れない

- 回答は「番号. 選択肢本文」の完全一致に近い形式で検証しているが、約3分動画の5条件はvalidationで失敗した。
- 当日メモでは、Answerの再実行で、モデルが選択肢ではなく**出力形式の説明用プレースホルダーをそのまま返した**ことを確認している。
- 解決案として「番号だけを返させる」、失敗時のraw outputを保存する、動画長やchunk設定で発生条件を切り分けることが挙がった。原因が確定したわけではない。
- 小林さんに出力挙動について相談する案が挙がった（当日メモ表記「小林S」）。

### 4. Summaryの肥大化と重要イベントの消失

- baselineでは各chunkについて、直前までのSummaryと現在のSituationを使って**累積Summary全文を書き直す**。
- 動画が長くなるにつれ、Memoryが大きくなり推論コストが増すことや、過去の重要イベントがSummary中で薄れたり脱落したりする可能性が問題になった。
- 当日メモには、同じ説明の反復、後半Summaryから前半の内容が抜けたように見える例がある。w8は出力token上限に達していないため、劣化を上限到達のみに帰することはできない。
- 議論では、Summaryとは別に、**発生した重要イベントを独立して追記・保存する**簡易な機構を試作する案が出た。将来の回答でイベント記録も参照できるようにする発想で、十分な比較や評価はまだ行われていない。

### 5. 関連研究の調査方針：何を調べるかを先に絞る

- 「他の研究では、過去のイベントをどう保持しているか」「Memoryへ何を・どう保存するか」のように**調査観点を一つに絞って**、10〜20本程度の関連論文を見比べることを勧められた。
- どれか一つ、関連性が高く質の確かな代表論文を選び、そのRelated Workを掘る。StreamAgentはその入口として話題に挙がった。
- 既存研究の仕組み・制約・自研究との違いを説明できる状態を目指す。関連研究を全て無差別に読むのではなく、「この問いに答えるか」で取捨選択する。
- Textとして保存するのか、視覚表現/KVなどか、イベントが消えないようどう管理するか、Memoryの数と使い分けを比較する。会話ではKV cacheの内部実装まで今すぐ理解する必要はない、という趣旨の発言もあった。
- 緒方さんへ論文の比較・検討の方法を相談する案も挙がった。
- **研究上の差分はまだ示せていない**。単に3-Agentを動かしたことと既存研究を超えることを区別し、類似する方法が既にあるかを確認する。

### 6. 予習Agent・未来の質問に備えるMemory（未決の発想）

- 学習データにどんな質問が多いかを事前に調べ、「将来問われそうな内容」を予習するAgent/方策が考えられるのではないか、というアイデアを議論。
- 例えばchunkごとに、予習した関心事項に対応する出来事が観測されたかを確認し、重要な記憶として保存するか判断する発想。
- これは**提案段階**であり、学習方法、Agent構成、研究新規性や実験での効果は未確定。現在の実験設定で「Questionは動画開始時から既知」である点と、質問が後から与えられる方式を混同しない。
- 「予習Agentに類似する既存論文があるか」を文献調査の具体的な問いとする。

### 7. 発表準備と用語の整理

- 動画処理単位について、現行のwindowという呼称をchunkへ統一する案。先行研究でのwindow/clip/chunkの用法を確かめて変更する。
- 当日メモでは「はじめに・関連研究」の準備が未完了。30日の発表に向けてスライドを段階的に作る話が出た（時刻・日程の細部は音声認識上不鮮明）。
- Situation/Summaryの結果や途中のMemoryの変化を、表やブラウザUIで追えるようにする案。

## 決定事項・合意した方向

1. **Situation → Summary → Answerを最小baselineとして扱う**。動作の確認と、以降の改良・比較のための出発点であり、新規性の主張ではない。
2. **実行時間はAgent別・chunk別に分解して原因を調べる**。動画長・処理数・sampling・token数も分かるようにする。
3. **3-AgentのPromptとAnswerの出力形式を改善する**。既存論文のPrompt・Appendixを参照し、出力を確認する。
4. **Memory・イベント・予習に関する既存研究を、一度に一つの具体的な問いへ絞って調査する**。特に「重要イベントをどう保存・保持するか」を入口とする。
5. **累積Summary以外に重要イベントを別記録する小さな試作**を検討・実施する方向。仕様や実験効果までは確定していない。
6. 発表スライドの構成も並行して準備する。

※「重要イベント記憶の方式を最終採用」「予習Agentの学習方式を決定」「特定手法が未解決と判明」といった決定は、今回の記録からは確認できない。

## 未解決・確認を要する事項

- 長い実行時間の主因はSummary入力肥大化、生成token数、Agent呼び出し回数、それ以外のどれか。条件間の所要時間の差の原因帰属。
- Answer失敗を起こしたPrompt・モデル出力・validationの条件。出力形式失敗と回答内容の正誤の区別。

- 保存形式別（Text/Visual/KV）・選択方策別（規則/Agent）・更新方式別（append/rewrite/merge/retrieve）の先行研究の到達点。
