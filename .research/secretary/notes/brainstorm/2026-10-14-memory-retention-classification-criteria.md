# Memory保持形式の分類：判定基準（当てはめ前の確定版）

## 位置づけ

- 大枠の軸「Memory保持形式」について、論文を当てはめる**前に**、判定の手順を固定するための記録。
- 固定するのは**判定の手順**（Memoryの定義、判定の問い、分割・統合の条件、根拠の付け方）だけ。小分類は暫定とし、論文への当てはめ結果に応じて追加・統合・修正する。
- [2026-10-14 Memory分類7軸メモ](2026-10-14-streaming-videoqa-memory-taxonomy-axes.md)のI/R/G/S/W/U/Q 7軸は**旧案**。現在は「軸 → 分類 → 小分類 → 該当論文」の階層を採り、Memory保持形式の下に分類A〜Gを置く（当初は粗い3分類A / B / Cで始め、2026-10-14に管理方式CをC〜Gの5分類へ分けた）。旧案の中身は必要時の候補として参照するに留める。
- 本書は探索記録であり、spec・実装指示・確定した学術taxonomyではない。

## コード体系

- **分類**には、軸をまたいで通しのアルファベット（A / B / C / D …）を振る。内容の頭文字（旧I/R/M）は使わない。
  - 理由：今後Memory以外の軸（Agent、Observation / Streaming入力、Anticipation / Planning）も分類して統合する際、頭文字だと記号が重複・混同しやすいため。
  - Memory保持形式：A（記憶する情報）、B（表現形式）、C（書き込みタイミング）、D（書き込みの選別）、E（更新）、F（構造）、G（読み出し）。
  - 次に追加する軸の分類はHから続ける。
- **小分類**は「分類のアルファベット＋通し番号」（例：A1、B3、F2）とする。
  - 同じ小分類の中の変種は小文字の枝番を付ける（例：A3a / A3b）。
  - 1つの分類の小分類が多くなりすぎないよう、分類内でまとまりが分かれる場合は分類そのものを分けて新しいアルファベットを振る。
  - 番号の振り直しを行った場合は、旧コードとの対応表を残す。

## 目標とする成果物の形

1. 分類ごとの表：`小分類コード | 何の情報・形式か | 具体例 | 該当論文（原著リンク）`
2. 論文別の対応表（1論文1行、複数所属可）：
   `論文（原著リンク） | 発表先 | A | B | C | D | E | F | G | 処理設定 | Query時点 | 区切り方 | 判断主体（書き込み／読み出し） | 容量上限 | 根拠の確かさ | 備考`
   - 分類ごとの表を先に置き、該当論文は短い論文名のリンクで並べる。論文別の対応表は付録に回す。
   - offlineの論文（動画全体を見られる設定）は、分類の表で論文名の後ろに `★` を付ける。
3. 分類の変更履歴：`日付 | 変更（追加・分割・統合・名称変更） | 理由 | 根拠論文`

## 共通ルール

### 基準0：何を「Memory」と数えるか

> ある時点で生成され、**現在の入力範囲を越えて、後の時点で利用される情報**をMemoryとする。

- 含めない：1回の推論（forward）の中だけに存在するKV cache。
- 含めない：入力フレームの選択（frame sampling）だけの工夫。これはObservation / Streaming入力の軸で扱う。
- 理由：これを除かないと、ほぼ全てのVLMが「KV Memoryあり」に分類されてしまう。

### 基準1：判定の根拠

- Abstractの名称（例：「event memory」）ではなく、Methodの記述と中心図に示された**実際に格納されるデータ構造**で判定する。
- 名称と中身がずれる場合は中身を優先し、ずれを備考に書く。

### 基準2：1つの分類には1つのコード（2026-10-14改定）

- 目標は、**1本の論文に、1つの分類から1つのコードだけ**を付けること。次の順に適用する。
  1. **当たり前の方式はコードを付けない**：各分類の「既定」（例：選ばない、追記のみ、全部渡す）はコードなし（`—`）とする。
  2. **よくある組み合わせには名前を付ける**：2つのコードの組み合わせが2本以上の論文で出たら、その組み合わせを1つの「複合」コードにする。
  3. **補助的な要素は記録しない**：検索の目印にだけ使うデータ（例：captionのembedding）はコードにせず、備考に書く。
  4. 上の3つで1つにならない場合（その組み合わせが1本だけ）は、論文の中心となるMemoryのコードを付け、残りは備考に書く。
- 当初の「一つの論文が複数の小分類に入ってよい」「補助に `(補)` を付ける」は、この改定で置き換えた。

### 基準3：根拠の確かさ

| 記号 | 意味 |
| --- | --- |
| `原文` | Method節・中心図・実験で確認した |
| `AI推定` | Abstract・Introduction程度からの推定 |
| `未確認` | 判断材料がない |

- AIだけで最初の表を作る段階では `AI推定` が多くなる。後で原文を確認する際の目印にする。
- 論文について記述する際は、著者の主張・実験で示されたこと・私たちの推論・未確認を区別する。

### 基準4：論文リンクの優先順位

学会・論文誌で発表されている論文は、**発表先の公式ページ**を原著リンクとして優先する。

1. 学会・論文誌の公式ページ
   - CVPR / ICCV / WACV など：CVF Open Access
   - ECCV：ECVA または Springer
   - NeurIPS / ICLR / ICML など：公式proceedings または OpenReview
   - ACL / EMNLP / NAACL など：ACL Anthology
   - AAAI / IJCAI / 論文誌：各公式ページ
2. 上記が見つからない、または未発表の場合：arXiv
3. 補助として、arXiv版や著者コードを「備考」に併記してよい。

- 対応表の「発表先」欄には、学会名・年（例：CVPR 2026）または `arXiv（採録未確認）` を書く。
- 採録の有無を確認できない場合は、採録済みと書かない。

## 分類 A：記憶する情報（What）

**判定の問い：** Memoryの1件分を取り出したとき、それは**世界の何について**の記録か？

| コード | 小分類 | 定義 | 例 |
| --- | --- | --- | --- |
| A0 | 映像そのもの | 映像を保存するだけで、何が映っているかは書かない | フレーム、視覚token、KV |
| A1 | 場面の説明 | 場所・人や物・動作を、文章などでまとめて書く | 「夜のキッチンで男性がカップを持ち上げた」 |
| A2 | 人・物ごとの記録 | 人や物1つにつき1件の記録を持ち、時間を通して追う | 「人物#3：赤い服、0:12に登場、今は机の横」 |
| A3a | イベント：区切りに使うだけ | イベント（ひとまとまりの出来事）の切れ目で保存単位を分けるが、中身は映像そのもの | イベントごとにまとめた視覚token |
| A3b | イベント：出来事を記録 | イベントごとに「何が起きたか」を書く | 「0:30–1:10 料理を盛り付けた」 |
| A4 | タスクの状態 | 質問への取り組みの途中経過を書く | 過去のQA、仮説、未確認事項 |

判定ルール：
- 映像と記述の両方を残す場合は、**記述の側**のコードを付ける。映像も残していることはBで分かる。
- A3aは「映像そのもの」を含むので、A0とは併記しない。
- 文中に人や物が**出てくるだけ**ならA1。人や物ごとの**記録欄があり、同じ個体を追い続ける**ならA2。
- 固定区間ごとの文章（例：2秒ごとのcaption）はA3bにしない。A3bは、区間がイベントとして扱われる場合（区切り方が固定時間以外、または区間にイベントとしての要約が付く）に限る。
- 「質問に関係する内容を選んで書く」ことは内容の種類ではないので、Aではなく分類D（D1）で表す。

### イベントの扱い（A3a / A3b）

イベントについては次の2つの問いが独立しているため、1つの記号にまとめない。

| 問い | 選択肢 | 記録先 |
| --- | --- | --- |
| (a) 区切りの根拠 | 固定時間 / 見た目の変化 / 意味の変化 / 学習したモデルの判断 | 「区切り方」の列 |
| (b) 保持する中身 | 映像だけ → A3a / 「何が起きたか」も書く → A3b | 分類A |

- 私たちのbaselineの課題（累積Summaryの中で出来事が薄れる・抜ける懸念）に直接関係するのはA3b側。ただし、この懸念自体は未検証。

## 分類 B：表現形式（How represented）

**判定の問い：** 格納されているデータの型は何か？ 次の順に問い、最初に当てはまったものを採る。

1. 人が読めるか？ → 読める：文章（B1）／欄に分かれたテキスト（B2）／点と線（B3）
2. 読めない → 画素そのものか？ → B4
3. 画素でない → 視覚エンコーダの出力か？ → B5
4. そうでない → LLMが入力を読んだときの内部データ（key/value）か？ → B6
5. そうでない → 決まった大きさの数値を毎回更新しているか？ → B7

| コード | 小分類 | 定義 | 例 |
| --- | --- | --- | --- |
| B1 | 文章 | 自由に書いた文 | caption、累積Summary（私たちのbaseline） |
| B2 | 項目付きテキスト | 時刻や内容が欄に分かれたテキスト | JSON、表、時刻付きイベント記録 |
| B3 | グラフ | 物と関係を点と線で表す | 「人 →持つ→ カップ」 |
| B4 | 画像 | フレームを画像のまま残す | 代表フレーム |
| B5 | 視覚特徴 | 画像をエンコーダで数値に変換して残す | 視覚token |
| B6 | KV cache | LLMが過去の入力を読んだときの内部データを残す | 過去clipのkey/value |
| B7 | 内部状態 | 決まった大きさの数値を毎回更新して持ち越す | memory token、hidden state |
| B8 | 項目付きテキスト＋画像（複合） | 項目付きテキスト（B2）と、その根拠になる画像（B4）を組で持つ | 「区間・caption＋代表フレーム」 |
| B9 | テキスト＋KV（複合） | 文章または項目付きテキスト（B1・B2）と、過去入力のKV（B6）を並行して持つ | テキストの要約＋検索用のKV |

判定ルール：
- B1とB2の境界：時刻や項目を**独立した欄**として持つならB2、文中に時刻が書かれているだけならB1。
- Bは**保存形式**で判定する。LLMへ渡すときの形式が違う場合は備考に書く（例：保存はグラフ、渡すときは文章）。
- 検索の目印にだけ使うembeddingなどはコードにせず、備考に書く。

## 分類 C：書き込みタイミング（いつ書くか）

| コード | 小分類 | 定義 |
| --- | --- | --- |
| C1 | 届くたび | フレームが届くたびに書く |
| C2 | 一定間隔 | 数秒ごとなど、決まった間隔で書く |
| C3 | 切れ目で | 映像が変わった所で区切って書く |
| C4 | 短期は届くたび・長期は切れ目で（複合） | 届いたものをまず短期Memoryに入れ、切れ目ごとに長期Memoryへ移す |

## 分類 D：書き込みの選別（何を残すか）

| コード | 小分類 | 定義 |
| --- | --- | --- |
| — | 選ばない（既定） | 届いたものをそのまま残す |
| D1 | 質問に関係するもの | 実際の質問に関係する内容を選んで残す |
| D2 | 質問に依存しない重要度 | 質問が分からないまま、汎用の物差しで「役立ちそうなもの」を残す（注目度・仮の質問・頻度・学習した方針） |

- 旧C4「似たものを減らす」はE2「まとめる・縮める」に統合した。該当した3本（StreamMem、Flash-VStream、VideoAgent）はいずれも、似たものを**捨てる**のではなく**まとめる**方式で、E2と常にセットで出ていたため（分類間の重複）。
- 誰が選ぶか（規則・学習モジュール・LLM・Agentなど）は「判断主体」の列で表す。

## 分類 E：更新（既存のMemoryをどう変えるか）

| コード | 小分類 | 定義 |
| --- | --- | --- |
| — | 追記のみ（既定） | 既存は変えず、新しい記録を足すだけ |
| E1 | 全体を書き直す | 毎回Memory全体を作り直す（私たちのbaseline） |
| E2 | まとめる・縮める | 似た記録を1つにする、データ量を減らす |
| E3 | 捨てる・入れ替える | 古い・不要な記録を消す、別の記録と入れ替える |
| E4 | まとめて、溢れたら捨てる（複合） | E2で縮めたうえで、容量を超えたらE3で捨てる |

- 追記のみの論文が際限なく大きくなるかは「容量上限」の列で表す。

## 分類 F：構造（どう配置するか）

| コード | 小分類 | 定義 |
| --- | --- | --- |
| — | 時刻順に並べるだけ（既定） | 記録を時間順に並べるだけ |
| F1 | 短期と長期に分ける | 直近の詳しい記録と、古い記録の置き場を分ける |
| F2 | 親子の階層 | 粗いまとめ（親）と細かい記録（子）をつなぎ、子も実際に読み出せる |
| F3 | 並列ストア | 同じ時間を、細かさや見方の違う複数のMemoryに同時に保存する（親子のつながりはない） |

- 「tree」「hierarchical」と名乗っていても、子を実際に読み出さないならF2にしない（基準1：名称より中身）。

## 分類 G：読み出し（回答時にどう使うか）

| コード | 小分類 | 定義 |
| --- | --- | --- |
| — | 全部渡す（既定） | Memory全体をLLMに入力する |
| G1 | 検索して一部渡す | 時刻・意味・質問で選んだ記録だけを渡す |
| G2 | 詳細を見直す | 保存済みの画像・特徴をもう一度見る |
| G3 | 検索してから詳細を見直す（複合） | G1で記録を選び、その記録の保存済み画像・特徴をG2で見直す |

- 元動画そのものを見直せるかどうかは「処理設定」の列（offline）で表す。

## 論文に付ける設定の列（Memoryの小分類ではない）

| 列 | 値 |
| --- | --- |
| 処理設定 | streaming（未来を見ず逐次処理） / offline（動画全体を参照可能） / 未確認 |
| Query時点 | 開始時から既知 / 途中で到着 / 未知 / 未確認 |
| 判断主体（書き込み） | 規則 / 学習モジュール / LLM・Agent / モデル自身の生成 / 未確認 |
| 判断主体（読み出し） | 規則 / 学習モジュール / LLM・Agent / モデル自身の生成 / 未確認 |
| 容量上限 | あり / なし（際限なく増える） / 一部あり（Memoryによって違う） / 未確認 |

- 判断主体は「書くか・何を読むかを誰が決めるか」を表す（2026-10-14採用）。
  - 規則：固定の手順や閾値で決まる（例：8秒ごと、類似度が閾値以上）。
  - 学習モジュール：学習した専用の小さなネットワークが決める。
  - LLM・Agent：LLMが推論やツール呼び出しで決める。
  - モデル自身の生成：回答と同じモデルが、出力tokenとして記録を書き出す。
- Agentの役割は将来の大枠「Agent」軸で扱う。この列はその材料にする。

- online / offlineの両方を同じ表に含め、この列で区別する。Memoryの方式は両者で共通する部分が多いため。
- offlineの論文は過去映像を後から見直せる前提が多い。私たちの設定（chunk-level causal、Questionは開始時に既知）とは性能を直接比較せず、参考にする仕組みとして扱う。

## 分割・統合・保留の判定条件

| 判断 | 条件 |
| --- | --- |
| 分割する | 同じ小分類の中に、Method図のレベルで明確に違うデータの流れが**2本以上の論文で**あり、かつその違いが研究の問い（古い情報の脱落・イベントの保持）に関係する |
| 分割を検討する | 1つの小分類に全体の半分以上の論文が集中している |
| 統合する | 2つの小分類の該当論文がほぼ同じ顔ぶれ、またはほとんどの論文でMethodから区別できない |
| 保留 | 該当が1本だけ → 小分類は作らず、「単独例」として備考に残す |
| 未確認 | 該当が0本 → 「存在しない」と断定せず「未確認」とする |
| 分類間の重複を疑う | 別の分類の小分類と常にセットで現れる → 独立した基準でない可能性を検討する |

## 調査の進め方

- 方式：判定の手順は固定し、小分類は暫定のまま回す。
  - 小分類まで先に固めると、論文のない分類が生まれやすい。
  - 判定の手順を固めずに回すと、回ごとに判定がぶれて全論文の分類をやり直すことになる。
- 1回目：代表論文10〜15本に当てはめ、上の条件に照らして小分類を修正する。
- 2回目：論文を追加して当てはめる。新しい論文を入れても新しい小分類がほとんど出なくなったら止める。
- 10/30中間発表を考慮し、回すのは2回、多くても3回まで。
- 小分類を変更するたびに、変更履歴に理由と根拠論文を残す。
- 論文数そのものは目標にしない。
