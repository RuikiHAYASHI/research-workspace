# Memory保持形式の分類：判定基準（当てはめ前の確定版）

## 位置づけ

- 大枠の軸「Memory保持形式」について、論文を当てはめる**前に**、判定の手順を固定するための記録。
- 固定するのは**判定の手順**（Memoryの定義、判定の問い、分割・統合の条件、根拠の付け方）だけ。小分類は暫定とし、論文への当てはめ結果に応じて追加・統合・修正する。
- [2026-10-14 Memory分類7軸メモ](2026-10-14-streaming-videoqa-memory-taxonomy-axes.md)のI/R/G/S/W/U/Q 7軸は**旧案**。現在は「軸 → 分類 → 小分類 → 該当論文」の階層を採り、Memory保持形式の下に粗い3分類（A / B / C）を置く。旧案の中身は必要時の候補として参照するに留める。
- 本書は探索記録であり、spec・実装指示・確定した学術taxonomyではない。

## コード体系

- **分類**には、軸をまたいで通しのアルファベット（A / B / C / D …）を振る。内容の頭文字（旧I/R/M）は使わない。
  - 理由：今後Memory以外の軸（Agent、Observation / Streaming入力、Anticipation / Planning）も分類して統合する際、頭文字だと記号が重複・混同しやすいため。
  - Memory保持形式：A（記憶する情報）、B（表現形式）、C（管理方式）。
  - 次に追加する軸の分類はDから続ける。分類の統合・分割でアルファベットが空いても、既存の記号は振り直さない（変更履歴で追跡する）。
- **小分類**は「分類のアルファベット＋通し番号」（例：A1、B3、C12）とする。
  - 同じ小分類の中の変種は小文字の枝番を付ける（例：A4a / A4b）。
  - 分類内のグループ（Cの「書き込み」など）は見出しで示し、記号には含めない。

## 目標とする成果物の形

1. 分類ごとの表：`小分類コード | 何の情報・形式か | 具体例 | 該当論文（原著リンク）`
2. 論文別の対応表（1論文1行、複数所属可）：
   `論文（原著リンク） | 発表先 | A：情報 | B：表現 | C：管理 | 処理設定 | Query時点 | 区切り方 | 根拠の確かさ | 備考`
3. 分類の変更履歴：`日付 | 変更（追加・分割・統合・名称変更） | 理由 | 根拠論文`

## 共通ルール

### 基準0：何を「Memory」と数えるか

> ある時点で生成され、**現在の入力範囲を越えて、後の時点で利用される情報**をMemoryとする。

- 含めない：1回の推論（forward）の中だけに存在するKV cache。
- 含めない：入力フレームの選択（frame sampling）だけの工夫。これはObservation / Streaming入力の軸で扱う。
- 理由：これを除かないと、ほぼ全てのVLMが「KV Memoryあり」に分類されてしまう。

### 基準1：判定の根拠

- Abstractの名称（例：「event memory」）ではなく、Methodの記述と中心図に示された**実際に格納されるデータ構造**で判定する。
- 名称と中身がずれる場合は中身を優先し、ずれを備考に書く。

### 基準2：複数所属と主従

- 一つの論文が複数の小分類に入ってよい（例：テキスト＋KVなら B1 / B6）。
- 主に使うMemoryと補助的な要素を区別する。補助には `(補)` を付ける（例：検索インデックス用のembeddingだけなら `B5(補)`）。

### 基準3：根拠の確かさ

| 記号 | 意味 |
| --- | --- |
| `原文` | Method節・中心図・実験で確認した |
| `AI推定` | Abstract・Introduction程度からの推定 |
| `未確認` | 判断材料がない |

- AIだけで最初の表を作る段階では `AI推定` が多くなる。後で原文を確認する際の目印にする。
- 論文について記述する際は、著者の主張・実験で示されたこと・私たちの推論・未確認を区別する。

### 基準4：論文リンクの優先順位

学会・論文誌で発表されている論文は、**発表先の公式ページ**を原著リンクとして優先する。

1. 学会・論文誌の公式ページ
   - CVPR / ICCV / WACV など：CVF Open Access
   - ECCV：ECVA または Springer
   - NeurIPS / ICLR / ICML など：公式proceedings または OpenReview
   - ACL / EMNLP / NAACL など：ACL Anthology
   - AAAI / IJCAI / 論文誌：各公式ページ
2. 上記が見つからない、または未発表の場合：arXiv
3. 補助として、arXiv版や著者コードを「備考」に併記してよい。

- 対応表の「発表先」欄には、学会名・年（例：CVPR 2026）または `arXiv（採録未確認）` を書く。
- 採録の有無を確認できない場合は、採録済みと書かない。

## 分類 A：記憶する情報（What）

**判定の問い：** Memoryの1件分を取り出したとき、それは**世界の何について**の記録か？

| 仮コード | 小分類 | 判定の目安 |
| --- | --- | --- |
| A0 | 意味を絞らない視覚内容 | フレーム・視覚token・KVをそのまま残し、何が写っているかを選んでいない |
| A1 | Scene（場面・環境） | 場所や全体状況の記述 |
| A2 | Entity（人・物体） | 個体ごとに同一性・属性・位置などを持つ |
| A3 | Action / State change（動作・状態変化） | 「何をした」「どう変わった」の記録 |
| A4a | Event：区切りの単位としてのみ使う | イベント境界でMemoryを区切るが、中身は意味を絞らない視覚内容 |
| A4b | Event：出来事の記述として保持する | 区間が「何の出来事か」をcaption・ラベル・開始/終了時刻などで持つ |
| A5 | Task-oriented（質問に向けた情報） | 質問に関係する証拠、仮説、予測、未確認事項 |

### Eventの扱い（A4a / A4b）

Eventについては次の2つの問いが独立しているため、1つの記号にまとめない。

| 問い | 選択肢 | 記録先 |
| --- | --- | --- |
| (a) 区切りの根拠 | 固定時間 / 見た目の変化（画像類似度・色分布など） / 意味的な変化 / Agentの判断 | 対応表の「区切り方」欄 |
| (b) 保持する中身 | 区間内の視覚内容だけ → A4a / 出来事の記述も持つ → A4b | A分類 |

- 例（既存メモの記述にもとづく `AI推定`、原文は未再確認）：
  - StreamForest：見た目の変化で区切り、視覚tokenだけを保持 → `A0 / A4a`
  - EventMemAgent：色分布の相関で区切り、区間ごとのcaptionと変化の記録も保持 → `A0 / A4b`
- 私たちのbaselineの課題（累積Summaryの中で出来事が薄れる・抜ける懸念）に直接関係するのはA4b側。ただし、この懸念自体は未検証。

## 分類 B：表現形式（How represented）

**判定の問い：** 格納されているデータの型は何か？ 次の順に問い、最初に当てはまったものを採る。

1. 人が読めるか？
   - 読める → 構造なし：B1 ／ フィールドや時刻を持つ：B2 ／ ノードとエッジ：B3
2. 読めない → 画素そのものか？ → B4
3. 画素でない → 視覚エンコーダの出力token・特徴か？ → B5
4. そうでない → LLM内部の層ごとのkey/valueか？ → B6
5. そうでない → 固定サイズで繰り返し更新される内部状態か？ → B7

| 仮コード | 小分類 | 例 |
| --- | --- | --- |
| B1 | Free text（自由文） | caption、累積Summary（私たちのbaselineもここ） |
| B2 | Structured text（構造化テキスト） | JSON、時刻付きイベント記録、項目を持つ記録 |
| B3 | Graph（グラフ） | event graph、entity graph |
| B4 | Raw frame（生フレーム） | keyframe、代表フレーム |
| B5 | Visual feature / token（視覚特徴・token） | 圧縮した視覚token、embedding |
| B6 | KV cache（時間を越えて保持されるもの） | 過去入力のkey/valueを残し、検索・再利用する |
| B7 | Latent / recurrent state（潜在・再帰状態） | memory slot、hidden state |

- 時刻だけが付いた文章（captionに時刻が付く程度）をB1とB2のどちらにするかは、1回目の当てはめで判断する未決事項とする。

## 分類 C：管理方式（How managed）

**判定の問い：** 時間が進むにつれて、Memoryに何が起きるか？

範囲が広いため、内部を4つのグループに分けて小分類に通し番号を振る。

### 書き込み：何を、いつ残すか

| 仮コード | 小分類 |
| --- | --- |
| C1 | 全部残す |
| C2 | 一定間隔で残す |
| C3 | 境界・変化があったときに残す |
| C4 | 類似度・冗長性に応じて残す |
| C5 | 質問との関連に応じて残す |
| C6 | Agentの判断で残す |

### 更新：既存のMemoryをどう変えるか

| 仮コード | 小分類 |
| --- | --- |
| C7 | 追記（append） |
| C8 | 全体の書き直し（rewrite） |
| C9 | 統合・圧縮（merge・compress） |
| C10 | 削除（evict） |

### 構造：どう配置するか

| 仮コード | 小分類 |
| --- | --- |
| C11 | 時刻順の一列 |
| C12 | 短期＋長期 |
| C13 | 階層 |

### 読み出し：回答時にどう使うか

| 仮コード | 小分類 |
| --- | --- |
| C14 | 全部渡す |
| C15 | 検索（時刻・意味・質問） |
| C16 | 元データの再参照 |

- 「何を基準に書き込むか」（C1〜C6）と「誰が判断するか」（規則・学習モジュール・LLM Agent）は混同しない。判断主体は備考に書く。C6は「判断基準をAgentに委ねている」場合に使う。
- 予想：Cは調査後に「構造」と「操作」へ分割される有力候補。ただし論文で確かめてから判断する。分割した場合、新しい分類には未使用の次のアルファベットを振る。

## 論文に付ける設定の列（Memoryの小分類ではない）

| 列 | 値 |
| --- | --- |
| 処理設定 | streaming（未来を見ず逐次処理） / offline（動画全体を参照可能） / 未確認 |
| Query時点 | 開始時から既知 / 途中で到着 / 未知 / 未確認 |

- online / offlineの両方を同じ表に含め、この列で区別する。Memoryの方式は両者で共通する部分が多いため。
- offlineの論文は過去映像を後から見直せる前提が多い。私たちの設定（chunk-level causal、Questionは開始時に既知）とは性能を直接比較せず、参考にする仕組みとして扱う。

## 分割・統合・保留の判定条件

| 判断 | 条件 |
| --- | --- |
| 分割する | 同じ小分類の中に、Method図のレベルで明確に違うデータの流れが**2本以上の論文で**あり、かつその違いが研究の問い（古い情報の脱落・イベントの保持）に関係する |
| 分割を検討する | 1つの小分類に全体の半分以上の論文が集中している |
| 統合する | 2つの小分類の該当論文がほぼ同じ顔ぶれ、またはほとんどの論文でMethodから区別できない |
| 保留 | 該当が1本だけ → 小分類は作らず、「単独例」として備考に残す |
| 未確認 | 該当が0本 → 「存在しない」と断定せず「未確認」とする |
| 分類間の重複を疑う | 別の分類の小分類と常にセットで現れる → 独立した基準でない可能性を検討する |

## 調査の進め方

- 方式：判定の手順は固定し、小分類は暫定のまま回す。
  - 小分類まで先に固めると、論文のない分類が生まれやすい。
  - 判定の手順を固めずに回すと、回ごとに判定がぶれて全論文の分類をやり直すことになる。
- 1回目：代表論文10〜15本に当てはめ、上の条件に照らして小分類を修正する。
- 2回目：論文を追加して当てはめる。新しい論文を入れても新しい小分類がほとんど出なくなったら止める。
- 10/30中間発表を考慮し、回すのは2回、多くても3回まで。
- 小分類を変更するたびに、変更履歴に理由と根拠論文を残す。
- 論文数そのものは目標にしない。
