# Streamingモデル選定の研究ストーリー

## 出発点

Streaming VideoQAの有力モデルを調べ、既存手法の公開コードを動かして理解する方針。10/30 MTGでは、まずストリーミング系のデータセット・ベンチマークを集め、その後、イベントをテキストとして記録する従来研究のコードを動かして問題を洗い出すことになった。

## 今回の調査から言えること

- 論文116本を調べたところ、多数のベンチマークが見つかった。これは一つの標準ベンチマークに集中しているというより、リアルタイム知覚、過去の記憶、応答タイミング、音声・会話文脈、自動運転など、測りたい能力・用途ごとに評価セットが作られているため。
- 繰り返し報告される主な共通軸はStreamingBenchとOVO-Bench。OVBenchやODV-Benchなど、別の能力や用途を測る評価もある。
- OneStreamerは比較表の範囲で、StreamingBench Real-Time 86.9、OVO-Bench Overall 72.1、OVBench 66.8、ODV-Bench 71.3など、複数ベンチマークにまたがる強い報告をしている。著者らは評価した8ベンチマークすべてで比較対象中の最高値と報告している。
- 一方、Watch-Think-InteractはOVO-Bench Overall 73.6を報告しているが、重み付き平均であり、OneStreamerの値などと単純比較はできない。評価条件・Overallの定義も論文間で一致しない。

根拠: [Streamingモデルの精度比較表](../../lab/projects/agentic-streaming-videoqa/papers/2026-11-02-streaming-model-benchmark-comparison.md)、[10/30 MTG議事録](../../lab/projects/agentic-streaming-videoqa/meetings/2026-10-30-mtg.md)、[OneStreamer](https://arxiv.org/abs/2610.01762)、[Watch-Think-Interact](https://arxiv.org/abs/2609.37035)。

## ストーリー案

「Streaming VideoQAの強い既存手法を選び、公開コードを動かして理解するため、論文群を横断してベンチマークと結果を調査した。評価セットは、ストリーミングで必要となる能力や対象領域ごとに多様化していた。その中で、共通して使われるStreamingBench・OVO-Benchに加えて複数の評価を報告し、今回の調査で特に幅広く高い成績を示したOneStreamerを、最初に動かす有力候補として選んだ。」

## 主張の強さと注意点

- 「界隈で唯一の最強」「どの評価でも最強」とは言わない。OneStreamerは幅広い評価で有力な候補だが、OVO-Benchでは集計方法の異なるより高い値も報告されている。
- 「ベンチマークの種類が多い理由」は、各論文がベンチマークに沿っているからだけでなく、現在理解・過去記憶・未来情報を待つ応答・音声統合・特定領域など、評価対象の能力が分かれているため、と説明する。
- 論文間の比較は自己報告値であり、フレーム数、fps、基盤モデル、Overall定義などの条件差を明示する。
- OneStreamerを動かす目的を、「絶対的な最強の証明」ではなく、「複数評価で有力な公開手法を実際に理解し、自分の研究と比較するための初期候補」と位置づける。

## まだ未決の点

- OneStreamerの実行結果を、どのベンチマーク・条件で自分の再現結果として報告できるか。
- 今回の研究目的である「イベントをテキストとして記録する手法の問題発見」に、OneStreamerの構成が適切な初期実装対象か。広い機能を持つモデルとしての再現と、記録・メモリ要素を分離して理解する比較は目的が異なる。
- 「長い間隔の記憶」を主に評価する場合、今回の主要ベンチマーク群だけで十分か。

## 2026-11-02 追記: ベンチマーク横断で強いモデルとメモリ表現

ユーザーの希望は、特定の課題に特化した手法から入るより、複数ベンチマークで良い成績を報告するモデルを起点に、テキスト・視覚トークン等の表現を広く理解すること。

### 候補

- **テキスト記録＋直近視覚窓: OneStreamer**。Qwen3-VL-4B。SB Real-Time 86.9、OVO Overall 72.1、OVBench 66.8、ODV-Bench 71.3等。論文は8評価すべてで比較対象中の最高値と報告。広く強い基準候補。
- **自然言語Memory＋過去映像の選択的再参照: Watch-Think-Interact**。Qwen3-VL-8B。SB 83.3、OVO weighted Overall 73.6。テキストの記録だけで完結せず、必要時に細かい過去映像を再参照する設計。OVO値の集計が重み付きなので単純順位には使わない。
- **視覚トークン＋階層メモリ: StreamReady**。Qwen2-VL-7B。SB RT 78.3、Omni 63.7、Contextual 48.2、Overall 63.4、OVO 68.2、OVBench 63.9、ProReady-QA 56.4等。複数のオンライン・オフライン評価がある。応答準備度の制御も設計の一部。
- **視覚・音声の証拠メモリ: StreamOV**。Qwen3-Omni-30B-A3B凍結。OVO Overall 64.0、SB RT 86.2、Omni 68.6。音声も扱う強い候補だが、バックボーンが大きく、純粋な視覚ストリーミングだけの比較ではない。
- **直近フレームだけの対照: SimpleStream / ViSS+TVS**。専用の長期Memoryを主役にしない設計でも、SimpleStreamはOVO RT 81.4 / SB RT 80.59、ViSS+TVSはOVO Overall 69.77 / SB RT 86.33を報告。明示的Memoryの効果を見るなら対照候補として重要。

### 現在の判断

最初の調査・再現候補としてはOneStreamerが最も合う。表現の違いも見たいなら、OneStreamer（テキスト記録を含むハイブリッド）とStreamReadyまたはStreamOV（視覚・マルチモーダル証拠の保持）を候補にし、SimpleStream等の直近窓ベースラインを参照に置く。ただし、モデル、バックボーン、学習データ、入力条件が異なるため、そのままのスコア差をMemory表現の効果とは解釈しない。

### 未決

- 複数手法を同一条件で動かして比較するのか、まず各公開実装を個別に再現して設計を理解するのか。
- どの実装・重みが実際に利用でき、手元の計算条件で再現可能か。
- 調査・再現の後、共通して残る弱点または性能差の原因をどう研究課題に絞るか。

## 次の判断

このストーリーは調査結果の導入として有力。モデル選定理由を説明するときは「複数のベンチマークで幅広く強い報告があり、公開実装を動かす価値があるため」とし、実行結果と再現条件を別途示す。

## 2026-11-02 追記: 論文目的とベンチマーク目的の二軸分類

### 出発点

分類を「論文が解こうとしている問題」と「ベンチマークが測ろうとしている能力」に分ける。両者は一対一対応しない。論文は複数の能力を対象にしたり、複数ベンチマークで評価されたりする一方、1つのベンチマークも複数能力を含むことがあるため、論文とベンチマークの分類を同じカテゴリに押し込まない。

サーベイ *Towards Online Interactors* は、応答の起動方式を **proactive**（モデル自身が応答開始を決める）と **reactive**（ユーザーの質問で応答する）に分け、タスクとして proactive narration・continuous state monitoring・event-conditioned response・proactive multi-turn interaction、reactive real-time perception・history backward tracing・future action prediction・contextual multi-turn QA を整理している。また reactive 手法を情報入力の間引き、working memory、長期Memory圧縮、質問時の履歴検索という処理段階でも分類している。これは本プロジェクトの表現・Memoryへの関心を補う有効な軸だが、論文目的の一次分類はまず proactive/reactive にするのが簡潔。

### 分類案A: 論文の目的

| 主分類 | 何を解く論文か | サーベイ上の下位タスク／論文例 |
|---|---|---|
| **Reactive: 質問時に過去を使って答える** | 映像を逐次取り込み、質問が来た時点までの情報から回答する | 現在の知覚、過去イベントの検索・時系列追跡、未来の行動予測、会話履歴をまたぐQA。例: STREAMCHAT、StreamMem、LiveVLM |
| **Proactive: モデルが適切な時点で話す** | 質問を待たず、何をいつ出力するかを判断する | ライブ描写、状態変化の更新、条件成立時の通知・応答、双方向の複数ターン対話。例: VideoLLM-online、ViSpeak、ProactiveVideoQAを主対象とする手法 |
| **基盤・効率化（横断タグ）** | 上の目的を、遅延・計算量・メモリ制約の下で実現する | 入力フレーム／視覚トークンの間引き、KV cache管理、長期Memory圧縮、履歴検索、イベントゲート、学習方式 |

主分類は論文の主張に基づいて1つを付け、必要なら副分類を付ける。たとえば OneStreamer のように幅広い能力を扱う論文は「主: reactive（ストリーム理解と質問応答）／副: proactive対応、効率化」のように記録する。メモリ形式（テキスト要約、視覚トークン、KV、イベント記憶、直近窓）は目的分類に混ぜず、独立した「手法・表現」タグにする。

### 分類案B: ベンチマークの目的

ベンチマークには、個々のベンチマークが明示するタスク分類を保持しつつ、横断比較用の能力タグを付ける。

| 主分類 | 測るもの | 代表例（例示。全タスクが単一分類とは限らない） |
|---|---|---|
| **現在のリアルタイム知覚** | 到着済み映像の現在状態・行動を理解できるか | StreamingBench Real-Time、OVO-Bench Real-Time、OVBenchの現在時点タスク |
| **過去記憶・履歴追跡** | 長い入力から過去の物体・行動・イベント・順序を検索できるか | OVO-Bench Backward、OVBenchのpast memory、時間的マルチターンQA系 |
| **未来予測・先読み** | 未来フレームを見ずに次の行動や結果を推定できるか | OVO-Bench Forward、OVBenchのfuture prediction |
| **応答タイミング・自発的応答** | 何を言うかだけでなく、いつ／話すべきかを判断できるか | ProactiveVideoQA、OVO-Bench Forward内の応答タイミング課題、MMDuet系 |
| **時間をまたぐ対話・マルチモーダル相互作用** | 複数ターンの整合性、音声・映像を含む対話、割り込みや応答の適切さ | StreamingBench Contextual / Omni-Source、SVBench、OmniMMI |
| **領域固有のオンライン理解** | 自動運転など、特定環境での対象・イベント・リスク・予測 | ODV-Bench（自動運転） |

これはベンチマーク名の置き換えではなく、目的の索引である。たとえば OVO-Bench は Real-Time／Backward／Forward の公式カテゴリを残したまま、上の横断タグを複数付ける。StreamingBench も Real-Time／Omni-Source／Contextual の公式構成を保持しつつ、知覚・マルチモーダル・対話のタグを付ける。OVBenchは過去・現在・未来に関する能力が横断するものとして扱う。したがって、公式スコアのカテゴリを独自の単一カテゴリに変換しない。

### 暫定的な提案

一覧表は次の二層にするのが使いやすそう。

1. **論文一覧**: 主目的（proactive / reactive / 両方を統合）、副目的、手法・Memory表現タグ。
2. **ベンチマーク一覧**: 公式タスク構成、主に測る能力タグ、Streaming条件（逐次入力・未来情報の制限・応答タイミングの採点有無）、対象ドメイン。

この形なら、たとえば「長期履歴の質問応答を目的とする論文が、過去記憶ベンチマークだけでなく現在知覚や対話ベンチマークでも評価されている」といった対応関係を別途見られる。Awesome リストは主にモデルとベンチマークを収録する索引であり、それ自体は統一的な目的分類を提供していない。したがって、Awesome の収録範囲を母集団の目安にし、目的分類の骨格はサーベイに沿わせる。

### 未決

- 「Reactive / Proactive」の二分類で、両方を備える統合モデルをどのように記録するか。主・副タグ方式が暫定案。
- StreamingBenchなどの公式カテゴリと、この横断能力タグを、一覧で併記する粒度。
- 長時間・長間隔の記憶を測るEgoProbe、EGOSTREAM、TeleEgo等をどの能力カテゴリに追加するか。既存調査では評価論文の確認が十分でないため、追加確認が必要。

## 2026-11-02 追記: VideoQAと非QAを分ける

### 気づき

Reactive / Proactive は「誰が応答を起動するか」の分類であり、「タスクがVideoQAかどうか」は別軸。ストリーミング理解には、質問に文章で答えるVideoQA以外に、ライブ描写、状態更新、イベント通知、応答タイミング判定、音声を含む対話などがある。したがって、最初にタスク／出力の形式を分類し、そのうえで起動方式を付ける。

### 改訂案: 論文目的を二段階で分類

**第1軸: タスク／出力形式**

| 分類 | 何をするか | VideoQAか |
|---|---|---|
| 質問応答（VideoQA） | 時点を指定した質問、またはストリーム中の質問に答える | はい |
| 複数ターン対話 | 映像についての連続質問、文脈・指示・発話履歴を保って対話する | QAを含む場合が多いが、対話全体はVideoQAに限らない |
| キャプション／実況／ナレーション | 映像の進行に合わせて説明・要約を出し続ける | いいえ |
| イベント通知／アラート | 条件や重要イベントを検出して知らせる | 通常はいいえ（質問応答を含む設計もありうる） |
| 状態追跡／継続更新 | 人数・物体状態など、指定された状態を継続的に更新する | 通常はいいえ |
| 予測／先読み | 次の行動や結果を推定する | 問われて回答する形式ならVideoQAの一種として扱えるが、予測タスクとして別タグも付ける |
| マルチモーダル音声対話 | 映像と音声を使い、発話・応答・割込みなどを含めてやりとりする | 質問応答に限定されない |

**第2軸: 応答の起動方式**

- **Reactive**: 質問や外部入力を受けて応答する。
- **Proactive**: モデルが応答の要否・タイミングを自律的に決める。
- **連続出力／常時更新**: 一定間隔または変化ごとに出力し続ける。サーベイのproactive側に含めて記録する場合もあるが、質問への応答でも状態更新でも成立するため、データ整理上は独立タグを残す。

この構造なら「VideoQAか／非QAか」と「Reactiveか／Proactiveか」を混同しない。例えば、質問に応じた過去記憶QAは「VideoQA + Reactive + 履歴検索」、イベント通知は「非QA + Proactive + イベント検出」、質問に応じた未来予測は「VideoQA + Reactive + 未来予測」と記述できる。論文に主ラベルを1つだけ強制せず、主タスクと副タスクを記録する。

### ベンチマーク側への反映

ベンチマークにも「QA形式か、非QA形式か」を独立した項目として持たせる。評価対象が同じでも回答形式が異なる可能性があるため、「評価能力」と「出力形式」は分ける。

例:

- OVO-BenchのReal-Time / Backward / Forwardは、時間的な理解能力のカテゴリ。質問への回答として評価されるので、基本的にはVideoQA系。
- StreamingBenchはReal-Time / Omni-Source / Contextualを持つ。ストリーミングQAに加え、音声・文脈理解を含む評価としてタグ付けする。
- ProactiveVideoQAは名前の通りQAを含むが、質問に答える能力だけでなく自発的な応答・タイミングも測るため、「VideoQA」と「Proactive応答」の両方を付ける。
- キャプション、継続状態更新、イベント通知を評価するベンチマークは、QA形式でなければ非QAとして整理する。

### 暫定判断

一覧の列は、論文・ベンチマーク双方で少なくとも「タスク形式（QA / 非QA / 混合）」を加える。論文目的の分類は「タスク形式 → 応答起動方式 → 能力タグ → 手法・Memory表現」の順で絞り込める形が見やすい。サーベイのReactive / Proactive二分法を維持しつつ、それがVideoQAそのものの分類ではないことを明示する。
